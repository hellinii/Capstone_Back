# 백엔드 구조 한눈에 보기 (처음 오신 분 먼저 읽기)

이 문서 하나면 **5분 안에** 이 백엔드가 뭘 하고, 코드가 어디 있고, 새 작업을 어디서 시작할지 알 수 있습니다. 코드를 처음 연다는 가정으로 씁니다.

---

## 1. 이 백엔드가 하는 일 (한 문단)

**ISO/IEC TS 4213** 기준으로 AI **분류 모델**의 성능을 평가하고 성적서를 발급하는 FastAPI 서버입니다. 사용자가 모델 예측 결과 파일(CSV/JSON)을 올리면 → ① **어떤 컬럼이 정답/예측/점수인지 파악**하고(LLM 자동 매핑, OpenAI) → ② **지표(정확도·정밀도 등)를 계산**하고 → ③ **결과를 자연어로 설명**하고(성적서 7·8·9절, Claude) → ④ **성적서를 발급**합니다. Render + Neon Postgres에 배포됩니다(§12).

## 2. 딱 한 장으로 보는 구조

> **핵심 규칙 하나만 기억하세요: `app/` 아래 폴더 = "하는 일(도메인)" 하나.**
> 그리고 **어느 도메인이든 파일 구성이 똑같습니다** → `router`(API) → `service`(흐름 조율) → 나머지(세부 로직) + `schemas`(그 도메인의 데이터 형태).

```
app/
├── main.py            앱 진입점 (uvicorn app.main:app) — 라우터 5개 연결, 시작 시 DB 준비
│
├── core/              🔧 모든 도메인이 공유하는 것
│   ├── schemas.py       공용 데이터 규격(enum·역할규칙·지표요건·"분석→평가" 인계 모델)
│   ├── database.py      DB 연결(SQLAlchemy) — 로컬 SQLite / 배포 Postgres
│   ├── parsing.py       업로드 파일(CSV/JSON) → 표(DataFrame) 변환 (공용 유틸)
│   ├── upload.py        업로드 경계 검사(확장자·크기 20 MiB·빈 파일) — 업로드 라우터 셋이 같이 씀
│   ├── concurrency.py   무거운 계산을 스레드풀로 넘기고 동시 실행 수를 묶음(이벤트 루프가 멈추지 않게)
│   └── llm_budget.py    LLM 호출의 시간당 총량 상한(넘으면 규칙 폴백, 429 아님)
│
├── analysis/          ① 분석 — 파일의 어떤 컬럼이 뭔지 파악 + 데이터 점검
│   ├── router.py            API: 컬럼 매핑 (/api/analyze-columns, /api/confirm-mapping)
│   ├── validation_router.py API: 데이터 검증 (/api/validate-data)
│   ├── analysis_service.py    흐름 조율(무키면 규칙매핑, LLM 실패하면 규칙매핑으로 강등)
│   ├── validation_service.py  데이터 검증 흐름 조율
│   ├── llm_mapper.py     LLM으로 컬럼 자동 매핑        fallback_mapper.py  규칙 기반 매핑
│   ├── reconcile.py      LLM이 준 컬럼명을 실제 헤더에 맞춤   metadata.py  클래스·분포 추출
│   ├── prompt_builder.py 매핑용 LLM 프롬프트          validator.py  매핑 유효성·계산가능 지표
│   ├── validation_checks.py  데이터 점검 항목들       schemas.py  이 도메인 데이터 형태
│
├── evaluation/        ② 평가 — 지표 계산
│   ├── router.py        API (/api/evaluate)          service.py  평가 흐름 조율
│   ├── engine.py        지표 → 계산함수로 분배          preprocessor.py  계산 전 데이터 정리
│   ├── report.py        결과 성공/실패 정리           schemas.py
│   ├── frame.py         평가에 들어갈 행을 정하는 규칙 한 곳   labels.py  클래스 표기·양성 기본값(§9.2·§9.4)
│   ├── errors.py        지표 계산 실패 표시 키 한 곳   environment.py  평가 환경(도구 버전·일시) 실측
│   └── metrics/         실제 지표 계산(sklearn): common·binary·multiclass·multilabel
│                        + counts(TP·FP 등 건수) · intervals(95% 신뢰구간) · misclassification(경계·확신 오류)
│                        · display(판정과 같은 쪽으로 읽히게 자릿수를 늘린 표시 문자열)
│
├── narrative/         ③ 서술 — 결과를 사람이 읽을 글로 (LLM: Claude Sonnet 5.5) — 자세히는 §10
│   ├── router.py        API (/api/narrative/jobs 새 경로 · /api/generate-narrative 옛 경로)
│   ├── jobs.py          작업 번호(job) — 만들기·실행(run_job)·조회·유실 판정   models.py  작업 표(narrative_jobs)
│   ├── generator.py     작업 경로 생성기 — 장별 동시 호출 + 칸별 검문 사다리
│   ├── legacy.py        옛 경로(한 번 호출, 얼려 둠 — 다음 라운드에 지움)   llm.py  Claude 호출 한 곳
│   ├── sections.py      소절 7칸 등록표             required_items.py  필수 서술 항목·결론 목록
│   ├── prompt.py        장별 지시문·칸 스키마        fact_view.py  AI 가 읽는 한국어 사실 시트
│   ├── checks.py        칸별 검사                   grounding.py  숫자 허용 목록·판정 모순
│   ├── fallback.py      규칙 템플릿(칸 함수 7개)     wording.py  조사·숫자 표기·클래스 이름(설명)
│   └── derived.py       서버 파생 계산    baselines.py  지표 참조 기준치    schemas.py
│
└── issuance/          ④ 발급 — 성적서 번호 채번·발급 (DB: 발급 표 — 서술 작업 표와 함께 DB 를 쓰는 곳)
    ├── router.py        API (/api/organization, /api/reports/issue·{no}·{no}/reissue·{no}/content)  service.py  발급 트랜잭션
    ├── models.py        DB 테이블(Organization·Report·ReportSnapshot·Issuance)  serializers.py  DB→응답 변환
    └── bootstrap.py     기본 기관 시드                schemas.py
```

DB 표는 모두 5개다 — 발급 4개(`organization`·`report`·`report_snapshot`·`issuance`, `issuance/models.py`)와 서술 작업 1개(`narrative_jobs`, `narrative/models.py` 의 `NarrativeJob`). 자세히는 §11.

> 💡 각 폴더의 `__init__.py`에는 그 도메인의 **파일 목차** 주석이 있습니다(나중에 생긴 파일이 빠져 있을 수 있으니 실제 목록은 위 나무를 보세요). 각 `.py` 파일 맨 위에는 **"이 파일이 뭐고 뭐랑 상호작용하는지"** 헤더 주석이 있습니다.

## 3. 요청이 흐르는 순서

사용자가 파일을 올리면 도메인을 **순서대로** 거칩니다. 이 흐름 = 위 폴더 순서입니다.

```
[예측결과 파일 업로드]
      │
      ▼
① /api/analyze-columns   analysis : 컬럼 역할 자동 파악 (LLM, 없으면 규칙)
      ▼
① /api/confirm-mapping   analysis : 사용자가 고른 매핑 검사 → 계산 가능한 지표 목록
      ▼  (선택) /api/validate-data  analysis : 계산 전 데이터 점검(결측·중복 등)
      ▼
② /api/evaluate          evaluation : 지표 계산
      ▼
③ POST /api/narrative/jobs narrative : 작업 번호 + 8.1 벤치마크 표를 바로 돌려주고, 서술은 뒤에서 만든다
③ GET  /api/narrative/jobs/{id}      : 단계(대기·생성 중·검사 중·다시 만드는 중·완료·실패)와 결과
      │    (옛 경로 /api/generate-narrative 는 옛 클라이언트용으로 얼려 둠 — 운영 프론트는 2026-10-23 배포부터
      │     작업 경로만 쓴다. 다음 라운드에 지운다)
      ▼
④ /api/reports/issue     issuance : 성적서 번호 발급 + DB 저장
   (발급 뒤 GET /api/reports/{no} 발급정보 · GET /api/reports/{no}/content 발급 시점 원본 · POST /api/reports/{no}/reissue 정정 발급)
```

- **LLM 을 쓰는 곳**: ①분석은 OpenAI(`OPENAI_API_KEY`, 모델 `MAPPING_MODEL` 기본 `gpt-6-luna`), ③서술은 Anthropic(`ANTHROPIC_API_KEY`, 모델 `NARRATIVE_MODEL` 기본 `claude-sonnet-5-5`). 키가 없거나 호출이 실패하면 자동으로 규칙 기반으로 대체돼서 서버는 안 죽습니다.
- **DB를 쓰는 곳**: ④발급 표와 ③서술 작업 표(`narrative_jobs` — 진행 단계·결과·내부 기록, 입력은 저장하지 않음). 나머지는 업로드 파일을 메모리에서 처리하고 끝(디스크 저장 없음).

## 4. 도메인 요약표

| 도메인 | 하는 일 | 주요 API | "진입점" 파일 |
|---|---|---|---|
| **core** | 공용 규격·DB·파일파싱 | — | `schemas.py`, `database.py` |
| **analysis** | 컬럼 파악 + 데이터 점검 | `/api/analyze-columns`, `/api/confirm-mapping`, `/api/validate-data` | `router.py` → `analysis_service.py` |

| **issuance** | 성적서 발급 | `/api/organization`, `/api/reports/issue`, `/api/reports/{no}`, `/api/reports/{no}/reissue`, `/api/reports/{no}/content` | `router.py` → `service.py` |

시스템: `GET /health` (상태 확인).

## 5. 새 작업을 어디서 시작하나 (신규 개발자용)

| 하고 싶은 것 | 열 파일 |
|---|---|
| API 동작/입출력 바꾸기 | 해당 도메인 `router.py` (얇음 — 검증·상태코드만) |
| 비즈니스 로직(흐름) 바꾸기 | 해당 도메인 `service.py` (서술은 `jobs.py`·`generator.py`, 옛 경로 `legacy.py`) |
| 요청/응답 필드 추가 | 해당 도메인 `schemas.py` (공용이면 `core/schemas.py`) |
| 새 지표 추가 | `evaluation/metrics/*` + `evaluation/engine.py`의 레지스트리 |
| 서술에 꼭 쓸 내용(항목·결론) | `narrative/required_items.py` — AI 지시문과 규칙 템플릿이 같이 읽는다(§10.3) |
| 서술 지시문 / 규칙 문장 | `narrative/prompt.py`(AI) / `narrative/fallback.py`(규칙 템플릿 — 칸 함수) |
| 서술 검사(숫자·판정 모순 등) | `narrative/checks.py`, `narrative/grounding.py` |
| DB 테이블 | `issuance/models.py`, `narrative/models.py` |

**패턴이 거의 같습니다**: 요청은 `router`(HTTP만) → `service`(흐름) → 세부 헬퍼로 흐릅니다. 예외는 서술(narrative)로, 흐름이 `jobs.py`(작업 번호) → `generator.py`(장별 생성·칸별 검문)와 옛 경로 `legacy.py` 에 있습니다(§10).

## 6. 실행 방법

```bash
python -m venv venv && source venv/bin/activate
pip install -r requirements-dev.txt

uvicorn app.main:app --reload      # → http://127.0.0.1:8000/docs (Swagger로 모든 API 확인)
venv/bin/python -m pytest -q       # 테스트 (tests/) — 맨 pytest 는 전역 파이썬을 잡을 수 있다(H-05)
```

환경변수: `OPENAI_API_KEY`(매핑 — 없으면 규칙 매핑), `ANTHROPIC_API_KEY`(서술 — 없으면 규칙 문장), `DATABASE_URL`(없으면 로컬 SQLite `data/app.db`). 서술 설정(`NARRATIVE_*`)은 §10.8, 전체 목록은 `.env.example`.

> 테스트는 `venv/bin/python -m pytest` 로 돌린다(zsh 에서는 `source venv/bin/activate` 가 듣지 않을 수 있다).

## 7. 알아두면 좋은 규칙

1. **import는 절대 경로** (`from app.analysis.llm_mapper import ...`).
2. **의존 방향은 항상 도메인 → core** (core는 도메인을 모름 → 순환 없음). 예외: 평가가 분석의 파싱/검증을 재사용(상류 참조)하는 것은 허용.
3. **`app/__init__.py`·`app/core/__init__.py`에 `import`를 넣지 마세요** — `main.py`의 `load_dotenv()`가 DB import보다 먼저 실행돼야 하는 순서가 깨집니다(파일 주석 참조).
4. **DB 스키마는 `init_db()`의 `create_all`로 생성**(마이그레이션 도구 없음).
5. 배포 구성은 §12(배포·운영) 참조.

## 8. 알려진 한계 (2026-09-07 확정)

여기 적힌 것들은 **버그가 아니라 의식적으로 그은 선**이다. 각 항목에 왜 그렇게 정했는지를
남긴다 — 근거를 잃으면 다음 사람이 같은 논의를 처음부터 다시 한다.

> **F-02·G-07·E-06 같은 번호**: 표와 코드 주석에 붙은 이런 번호는 예전 문제 대장(문제를 모아 번호를 매겨 고치던 목록)의
> 항목 번호다. 대장 자체는 저장소에 없고, 번호는 "언제 무슨 문제로 바뀐 코드인가"를 알려 주는 이력 표시로만 남겨 둔다.
> 뜻은 그 자리의 설명을 읽으면 된다.

### 8.1 성적서의 진본성 — 서버가 완전히 보증하지는 않는다 (F-02·F-03·F-05)

발급 시점의 성적서 원본(JSON + SHA-256)과 기관 스냅샷은 서버에 보관된다. 번호로
복원할 수도 있다. 그러나 **다음 셋은 구현하지 않았다.**

| # | 한계 | 왜 이번 범위에서 제외했나 |
|---|---|---|
| **F-02** | 평가와 발급이 서버에서 결속되지 않는다 — 평가를 거치지 않고도 정식 번호를 받을 수 있다 | 백엔드 단독으로 닫히지 않는다(프론트 필수·3단 롤아웃). 무엇보다 **기존 사용자 전원이 발급 불가**가 되고, 결속을 넣어도 **2행짜리 CSV 로 평가를 통과시켜 우회**할 수 있어 실효가 낮다 |
| **F-03** | 서술 API 가 클라이언트가 보낸 `fact_sheet` 를 다시 계산해 대조하지 않고 그대로 믿는다 — 작업 경로 `POST /api/narrative/jobs` 도 옛 경로 `/api/generate-narrative` 도 같다(형식·길이 상한 검사만 한다) | F-02 와 같은 뿌리다. 서버가 평가 결과를 갖고 있어야 대조할 수 있는데 그것이 F-02 다 — 따로 닫으면 반쪽이 된다 |
| **F-05** | 서버가 PDF 를 만들지도 보관하지도 않는다. 최종 산출물은 브라우저 인쇄물이다 | 서버 렌더링 스택(헤드리스 브라우저)이 필요하고 Render free 512 MB 안에서 운영 위험이 크다 |

**실질적 의미**: 발급된 성적서의 *내용*은 서버 사본으로 검증할 수 있지만, *그 성적서가
실제 평가를 거쳤는가*는 서버가 보증하지 않는다. 대외 제출용으로 쓸 때 이 점을 알고 써야 한다.

### 8.2 운영·인프라

| # | 한계 | 판단 |
|---|---|---|
| **G-03** | LLM 예산 상한이 **프로세스 로컬**이라 워커가 N개면 실효 상한도 N배 | 과허용 방향으로만 틀리므로 정상 사용자를 잘못 막지 않는다. 정확한 총량이 필요해지면 DB 카운터로 옮긴다 |
| **G-03** | 인증·레이트리밋 없음 | 인증은 넣지 않기로 확정했다(2026-09-07 제품 결정 — 대신 LLM 호출 총량에 시간당 상한, `core/llm_budget.py`). IP 리밋은 **프록시 뒤 실제 client IP 가 미관측**이라 보류 — 모든 요청이 같은 IP 로 보이면 IP 리밋이 전역 리밋으로 붕괴해 정상 사용자 1명이 전체를 막는다 |

| **H-05** | 맨 `pytest` 는 전역 anaconda 파이썬을 잡을 수 있다(fastapi/pydantic 버전이 `requirements.txt` 와 다름) | 프로젝트 venv(`venv/bin/python -m pytest`)는 `requirements.txt` 와 같은 버전이다(2026-10-22 확인). 그래도 Postgres·배포 조합의 최종 증거는 CI 다 |
| **G-07** | `DATABASE_URL` 이 없으면 휘발성 SQLite 로 내려가고 기동을 계속한다 | 하드 실패 가드는 `REQUIRE_PERSISTENT_DB=1` 로 **기본 꺼짐**이다. 프로덕션이 이미 SQLite 로 돌고 있다면 켜는 순간 서비스가 죽기 때문. 대신 `/health` 가 평시에도 `persistent` 를 싣고 기동 시 경고를 남긴다 |

### 9.1 규칙 폴백 매퍼 (OpenAI 키가 없거나 LLM 이 실패할 때)

`app/analysis/fallback_mapper.py` 의 `fallback_role` 이 컬럼 **이름만** 보고 역할을 고른다. 이름은 낱말로 쪼갠다 —
구분자(`_` `-` 공백 `.`)와 camelCase 경계(`imageId` → image, id). 순서대로 보고 처음 맞는 것을 쓴다.

1. 정답 이름(`y_true`·`label`·`target`·`ground_truth`·`actual`·`true_label(s)` …) → `y_true`(멀티레이블은 `true_labels`)
2. 예측 이름(`y_pred`·`pred`·`prediction`·`predicted`·`pred_label(s)` …) → `y_pred`(멀티레이블은 `pred_labels`)
3. 지연시간 이름(`latency`·`latency_ms`·`inference_time(_ms)`·`response_time(_ms)`·`elapsed_ms`, 또는 낱말 `latency`) → `latency`
4. 낱말 `id`·`idx`·`index`·`uid`·`uuid`, 또는 붙여 쓴 식별자 이름(`sampleid`·`rowid`·`userid`·`fileid` 등 목록) → `sample_id`. `valid_flag`·`width` 처럼 'id' 가 **들어 있기만** 한 이름은 잡지 않는다
5. 낱말 `prob`·`proba`·`probability`·`score`(복수형·숫자 꼬리 `probs`·`scores`·`prob1` 포함), 또는 `p_` 로 시작 → 유형의 확률 역할(`score_positive`·`prob_per_class`·`score_per_label`). 이진은 낱말 `positive` 도. `position` 같은 이름은 잡지 않는다
6. 그 밖은 `ignore` + "규칙으로 판단하지 못했다" 안내

한 컬럼만 받는 역할(샘플 ID·정답·예측·이진 확률·지연시간)을 두 번째 컬럼이 또 잡으면, 첫 컬럼만 그 역할로 두고
나머지는 `ignore` 로 내린 뒤 `column_notes` 에 `status="duplicate_role"` 안내를 싣는다 — 역할이 겹치면 매핑 확정이
막히기 때문이다. 단 이진에서 양성 확률 후보가 여럿(`prob_0`·`prob_1`)이면 기본 양성 클래스(§9.2)
이름이 붙은 컬럼을 남긴다 — 첫 컬럼을 남기면 음성 확률이 양성 확률로 들어가 AUROC 가 조용히 뒤집힌다. 이름이 맞는
후보가 없으면 첫 컬럼. 확률 역할은 클래스·레이블마다 한 컬럼이라 여러 컬럼을 그대로 받는다.

자동 매핑 AI 지시문(`app/analysis/prompt_builder.py`)도 다중·멀티 확률 컬럼을 확률 역할로 안내한다(종전에는
"확률 컬럼도 ignore"라고 적어 y_pred 없는 파일의 예측이 사라졌다). 지시문의 역할 집합은 `VALID_ROLES_BY_TASK` 와 같다.

### 9.2 양성 클래스 기본값

사용자가 양성 클래스를 고르지 않았을 때의 기본값은 `app/evaluation/labels.py` `default_positive_class` 하나에서 정한다.
자동 판단(`analysis/metadata.py`)·지표 계산·확률에서 예측 파생(`preprocessor.py`)이 모두 이 함수를 쓴다. 지표 계산은
`metrics/binary.py` 의 `_resolve_positive_value` 한 곳에서 양성을 정하고, Precision·Recall·F1(`metrics/common.py`
`_get_binary_kwargs`)·신뢰구간·혼동 수 집계도 그 함수를 부른다. 양성이 지정되면 그 표기의 원래 값(§9.4)을, 지정되지
않으면(metadata 없이 API 를 직접 부른 경우) 이 기본값을 쓴다.

1. 숫자면 큰 값(1 > 0)
2. 알려진 짝(yes/no·true/false·positive/negative·spam/ham·malignant/benign·fraud/normal …)이면 정해진 값
3. 그 밖은 정렬 순서(숫자면 수치 순, 아니면 사전 순)의 **뒤쪽** 값 — 임시로 고른 것이라 `positive_class_ambiguous=true` 로 알린다

종전에는 3번에서 자동 판단만 **앞쪽**을 골라 화면에 보인 양성과 성적서 수치의 양성이 달랐다('cat'·'dog' 이면 화면은
cat, 지표는 dog). 이제 셋 다 dog 다. 지난 평가는 저장된 양성 값을 쓰므로 영향이 없다. 양성 미지정일 때
Precision·Recall·F1 만 정렬 뒤쪽 값을 쓰던 예외도 없앴다(fraud/normal 이면 종전엔 그 셋만 normal 을 양성으로 봤다).
프론트는 양성을 늘 보내므로 화면 결과는 바뀌지 않는다.

### 9.3 검증 단계에서 미리 보는 것 (`/api/validate-data`)

- **확률 컬럼 이름**(`Probability column names`, error): 다중·멀티에서 예측 컬럼 없이 확률만 매핑하고, 고른 지표가 예측을
  쓰면 평가는 확률 컬럼 이름으로 클래스를 확정해 예측을 만든다. 이름으로 확정할 수 없으면(예: 클래스가 cat/dog 인데
  컬럼이 prob_a·prob_b) 종전에는 검증을 통과한 뒤 평가에서 400 으로 막혔다. 이제 평가와 **같은 함수**
  (`preprocessor.derivation_source`·`probability_names_problem`)로 검증이 미리 보고 막는다. 예측 컬럼이 있거나 이름이
  맞으면 항목을 내지 않는다. 이진은 확률 컬럼이 하나라 이름을 보지 않는다.
- **지연시간 단위**(`Latency unit`, warning): 지연시간 역할은 ms 로 읽는다. 값이 모두 1 미만이면 초로 적은 것으로 보여
  경고한다. 1 ms 미만으로 도는 모델도 있어 막지 않는다 — 단위는 데이터만으로 확정할 수 없다.
- **이진 클래스 수**(`Binary class system error`): 정답∪예측 클래스가 둘을 넘으면 error(평가도 400 으로 멈춘다 —
  `preprocessor._check_binary_classes`). 정답 클래스가 하나뿐이면 예측에 두 클래스가 있어도 warning(`found 1`, 평가는 계속).

### 9.4 클래스 표기

데이터의 클래스 값과 화면·API 가 주고받는 클래스 이름은 다를 수 있다. 빈 칸이 하나라도 있으면 pandas 가 정수 정답
컬럼을 float 로 읽어 1 이 1.0 이 되고, 문자열 클래스에는 앞뒤 공백(`' cat'`)이 붙어 있을 수 있다.

- **주고받는 이름은 표기 하나**: `app/evaluation/labels.py` `normalize_label` — 정수 값 float 는 소수점 없이(1.0 → `'1'`),
  앞뒤 공백은 뗀다(`' cat'` → `'cat'`). metadata 의 클래스 목록·`positive_class`, 응답의 `derived_prediction.positive_class`·
  `negative_class`, `confusion_counts.positive_class` 가 모두 이 표기다. 그래서 정답이 float 이면 양성은 `'1.0'` 이 아니라
  `'1'` 로 나간다(정수·문자열 정답은 종전과 같다). 이미 저장된 옛 run 의 metadata 에는 `'1.0'` 이 남아 있을 수 있다.
- **원래 값은 `find_label` 로 되찾는다**: `y_true == 양성` 처럼 데이터 값과 비교하는 곳은 `str()` 로 맞춰 보지 않고
  `labels.find_label(값들, 표기)` 로 원래 값(1.0·`' cat'`)을 찾아 쓴다. 쓰는 곳: 이진 예측 파생(`preprocessor.py`),
  `binary._resolve_positive_value`(§9.2). 다중 예측 파생은 같은 규칙으로 만든 표기 → 원래 값 표를 쓴다. 표기를 만들어
  내보내는 쪽(metadata 의 이진 클래스 판단·알려진 정답 목록·확률 컬럼 클래스 확정)은 `normalize_label` 을 쓴다.
- **검증의 클래스 불일치 검사는 평가와 같은 표기로 비교한다**: `validation_checks.check_class_mismatch` 는
  `normalize_label`(정수 값 float → 정수 표기, 앞뒤 공백도 지움)로 비교한다 — 평가 전처리와 같은 표기라 정답 1.0 과
  예측 1, 정답 `' cat'` 과 예측 `'cat'` 은 같은 클래스다. 표기가 실제로 바뀐 값은 `check_label_notation` 이 따로
  알린다(평가 경고와 같은 `label_notation_changes`). `normalize_label` 은 `label_text` 에 공백 제거를 더한 것이라 숫자
  표기 규칙은 한 곳에 있다.
- **평가 프레임의 라벨 값**(`preprocessor._normalize_hard_labels`): 정답·예측 하드 라벨을 한 표기로 맞춘 뒤 지표를 낸다.
  둘 다 빈 값 없는 정수 값 숫자(int, 1.0 같은 정수 float)면 **int64** 로 두고, 그 밖은 `normalize_label` 문자열로 바꾼다
  (`unify_hard_label_columns`). 숫자 라벨까지 문자열로 바꾸면 sklearn 이 지표마다 문자열 배열을 정렬해 80만 행(10MB)
  평가가 2초대에서 40초 넘게 걸렸다. 응답의 클래스 이름(M21 `labels`·M22 키·분포 키)은 어느 쪽이든 표준 이름 문자열이고,
  sklearn 에 넘기는 `labels` 는 `metrics.common.class_values` 로 이름 → 데이터 값을 찾아 쓴다.
- **불리언 라벨**(`preprocessor.align_boolean_labels`, 평가 전처리·검증이 같이 씀): `proba > 0.5` 를 그대로 저장한 True/False
  예측과 0/1 정답처럼 한쪽만 불리언이면 **예측이 정답 표기를 따른다** — 정답이 숫자(또는 표기가 0/1 뿐)면 예측을 1/0 으로,
  정답이 불리언이고 예측 표기가 0/1 뿐이면 예측을 True/False 로. 둘 다 불리언이면 `'True'`/`'False'` 그대로다.
  불리언인지는 dtype 이 아니라 값으로 본다 — 빈 칸이 섞여 object 로 읽힌 True/False 컬럼도 불리언이다.

## 10. 서술(7·8·9절) — 작업 번호 · 장별 생성 · 칸별 검문 사다리 · 규칙 템플릿 (2026-10, AI 서술 설계 구현 라운드)

한 줄 요약: **서술은 소절 7칸 단위로 만들고, 검사하고, 바꾸고, 기록한다.** 숫자·판정은 코드가 정하고, AI 는 코드가 뽑은
결론을 문장으로 옮긴다. AI 가 실패하거나 검사에 걸린 칸만 규칙 문장으로 바꾼다.

### 10.1 두 경로

| 경로 | 누가 쓰나 | 방식 |
|---|---|---|
| `POST /api/narrative/jobs` → `GET /api/narrative/jobs/{id}` (새) | 운영 프론트(2026-10-23 배포부터) | 작업 번호와 8.1 벤치마크 표를 **바로** 주고, 서술은 BackgroundTasks 의 `jobs.run_job` → `generator.generate_sections` 가 만든다. 품질 우선(effort `high`, 최대 10분) |
| `POST /api/generate-narrative` (옛) | 옛 클라이언트(운영 프론트는 더 이상 부르지 않음) | 한 번 호출로 일곱 칸을 받는다(`legacy.py` 에 그대로 얼림, effort `low`, 서버 마감 120초 — 넘으면 200 + 규칙 문장). 다음 라운드에 지운다 |

두 경로는 같은 사실 시트(`FactSheet`)·같은 숫자 허용 목록·같은 규칙 템플릿을 쓴다. 판정(verdict)은 늘 사실 시트 값이다(AI 가 정하지 않는다).

### 10.2 소절 7칸 (`sections.py`)

7.1 혼동행렬 해석 · 7.2 분포·불균형 · 7.3 추가 관찰 · 8.1 벤치마크 · 8.2 종합 총평 · 8.3 리스크 · 9 권고(9.1·9.2 서술 + 권고표가 한 칸).
7.3 은 결론 목록 밖에서 AI 가 찾은 것만 쓰는 칸이라 규칙 문장이 없다 — AI 가 쓰지 않았거나 검사에 걸리면 비우고 성적서가 "해당 없음"(고정 문구 15)을 찍는다.

### 10.3 필수 서술 항목과 결론 목록 (`required_items.py`)

성적서 절마다 반드시 다룰 항목 41개를 표로 둔다(항목 ID `7.1-01` … `9-03`). `select_items(사실 시트, 고객 입력, 작업 유형)` 이
이 성적서에 해당하는 항목만 남기고 숫자를 채운 **결론**을 만든다. **AI 지시문과 규칙 템플릿이 같은 목록을 읽는다** — 그래서
AI 가 쓸 내용과 규칙 문장이 쓸 내용이 어긋나지 않는다.

| 작성 주체 | AI 지시문 | 규칙 템플릿(`Conclusion.template_text`) |
|---|---|---|
| ai | '반드시 다룰 결론' | 결론 문장 그대로(서술체). 판정 사유·불균형·임계값 위험처럼 규칙 문장이 따로 있는 항목은 그 문장 |
| ai_fact (모델 용도·최약 클래스의 용도상 위험) | AI 가 해석 | **사실 문장만**("의뢰자가 밝힌 모델 용도는 '…'이다.") — 해석은 지어내지 않는다 |
| fixed_interpret (오분류의 성격·근소 차이 지표) | '해석만 쓸 결론' + 해석 재료(우세한 오류, 근소 지표가 충족했는지) | 성적서가 고정 문구 17·18 로 숫자를 찍으면 **숫자 없는 해석 한 문장**, 찍지 않는 옛 요청이면 숫자 문장 |
| fixed · form | '성적서가 따로 찍는 문장'(되풀이 금지) | 쓰지 않는다 |

- 고정 문구 16(8.1 표 아래, 프론트가 계산해 `facts.fixed_sentences` 에 `id "16"` 으로 보냄): 서술 지표 가운데 기준표에 없는 지표가
  **일부**면 "다음 지표는 내부 참조 기준치가 없어 벤치마크 비교를 하지 않았다: {지표}." — 지시문의 '성적서가 따로 찍는 문장'에 이 원문이
  실린다. **전부**면 "선택한 지표에 내부 참조 기준치가 없어 벤치마크 비교를 하지 않았다." — 8.1 칸은 출처 `fixed`·빈 글(아래 10.4).
  `facts` 가 없는 옛 요청과 옛 경로는 종전 문장("비교 가능한 내부 참조 기준치가 없어 벤치마크 비교를 생략한다.") 그대로.
  프론트는 판 3 성적서에서 8.1 이 출처 `fixed`·빈 글이면 자리표시자를 찍지 않고 표·고정 문구 16 만 그린다(계약 — 빈 8.1 을
  다른 출처로 보내면 화면이 "서술 없음" 자리표시자를 찍는다).
- 고객 입력 값이 "제공되지 않음"으로 **시작**하면 제공되지 않은 것이다(`wording.is_not_provided` 한 곳). 프론트는 "모름 + 덧붙이는 글"을
  "제공되지 않음 (의뢰자 제공: …)" 로 보낸다 — 괄호 안 글은 참고 글일 뿐이라 결론(예: 8.2-12 지표 선택 기준)을 살리지 않고, 지시문 규칙
  17 이 AI 에게 "의뢰자가 정했다·골랐다"고 쓰지 말라고 한다.
- "성적서가 17·18·16 을 찍는가"는 `required_items.code_prints` 한 곳에서 정한다. 새 프론트(사실 시트에 `facts` 가 있음)는 찍는다 —
  `facts` 가 상한을 넘어 고정 문장 목록을 비웠어도(`omitted.fixed_sentences`) 화면은 찍는다. 옛 프론트(`facts` 없음)는 찍지 않는다.
- 작성 규칙(아래 D37): 클래스는 `이름(설명)`(고객 입력 `class_label_descriptions`), 영어 코드값·필드명을 쓰지 않음, 서술체 완결
  문장(개조식·`항목: 값` 꼴 없음). 조사(은/는·으로/로)와 숫자 표기는 `wording.py` 한 곳. AI 지시문 규칙 8 은 영문·숫자 이름 뒤 조사를
  영어 발음의 끝소리로 고르게 한다(benign과, cat과, dog와, P3이 — 세션 C 실호출에서 'benign와'·'P3가'가 나왔다).
  조사 규칙은 프론트 `koreanJosa.josaWaGwa`(3절)와 같은 공통 규칙이다(세션 C 마지막 검토 — 같은 이름에 3절과 7.2 가 다른 조사를 찍었다):
  끝 따옴표·공백은 건너뛰고, '이름(설명)'은 괄호 앞 이름으로(2(정상)와), 숫자는 읽는 소리(소수는 끝 숫자, 정수는 십·백·천·만…),
  영문 대문자 끝은 알파벳 이름(L·M·N·R 만 받침), 소문자 끝은 -ng·-m·-n·-l·-ck 와 모음 뒤 -t 만 받침(cat과·malignant와·test와),
  정할 수 없으면 '와(과)'·'은(는)'. 같은 대조 표를 두 저장소 테스트(`tests/test_session_c_final_review.py`)에 박았다.
- 숫자 표기: 판정과 비교되는 값은 프론트가 판정과 같은 쪽으로 읽히게 만든 표시 문자열(`value_text`·`margin_text`·`*_text`)을 그대로,
  지표 값·목표값·구간 끝은 성적서와 같은 셋째 자리(목표와 같아 보이면 자릿수를 늘림), 그 밖의 실수는 넷째 자리.
  8.1 참조 범위 비교의 모델 값(규칙 문장·사실 시트 보기)은 그 표기가 범위 끝과 같아 위치 판정(반올림 전 값)과 반대로 읽히면 자릿수를
  늘린다(`required_items.benchmark_value_text` → `wording.range_value_text` — 0.79996 은 '0.8' 이 아니라 '0.79996, 참조 범위 0.8~0.92').
  규칙은 프론트 8.1 표(`judgedNumber.formatBenchmarkValue`)와 같다(세션 C 마지막 검토 — 최대 자릿수가 9·6 으로 달라 표와 서술 숫자가
  갈렸다): 최대 **여섯째 자리**, 그래도 반대로 읽히면 위치 쪽으로 자른다(아래는 내림·위는 올림). 판정 대상 지표면 같은 표기가 목표
  판정(충족/미달)과도 맞아야 하고, 둘 다 맞는 표기가 없으면 목표 판정이 우선(6.1 표기). 같은 대조 표를 두 저장소 테스트에 박았다.
  늘린 표기는 숫자 허용 목록에도 들어간다(`grounding.build_number_whitelist` 가 같은 함수를 부른다).
  응답의 벤치마크 표(`model_value`)는 계약대로 넷째 자리 숫자 그대로다.
- 오류 성격 해석 재료(7.1-11, 세션 C): 우세한 오류에 더해 근거 건수(확률이 있는 오분류·경계·확신·둘 다 아닌 오류 — 둘 다 아닌 건수는 두 오류가
  겹칠 수 없을 때만, `required_items.error_breakdown`)를 싣고 "문장에 쓰지 않는다"고 적는다. 오분류가 `ERROR_NATURE_MIN_COUNT`(10)건 미만이거나
  경계+확신 오류가 오분류의 과반이 아니면(두 오류가 겹칠 수 있으면 많은 쪽 하나로 본다) '상당 부분·대부분·우세한 성격' 같은 일반화를 막고
  "경계 오류가 확신 오류보다 많다" 수준만 쓰게 한다. '오류의 주된 성격으로 해석해도 된다'는 우세한 쪽 **하나**가 과반일 때만 싣고, 두 오류의
  합만 과반이면 "경계 오류와 확신 오류를 합치면 오분류의 절반을 넘는다"고만 쓰게 한다(세션 C 마지막 검토 — 20건 중 경계 6·확신 5 에
  '경계 오류가 절반을 넘는다'고 썼다).
  확신 오류가 오분류의 소수면 '확률이 높은 예측 전반을 믿을 수 없다'는 일반화를 막는다. 둘 다 아닌 건수는 생성기가 허용 목록에 넣는다.
- 근소 차이 지표(8.3-02, 세션 C): 해석 재료에 지표마다 신뢰구간이 목표값을 포함하는지(`ci_contains_target`)를 싣는다. 포함하지 않는 지표는
  AI·규칙 문장 모두 "표본이 달라지면 판정이 뒤집힐 수 있다"를 쓰지 않고 목표와의 여유가 작다는 사실만 쓴다(8.2 의 '구간이 목표와 떨어져
  있다'와 부딪치지 않게). 8.3 지시문은 여유·아슬아슬 해석을 사실 시트의 근소 차이 지표에만 쓰게 한다.
- 임계값 조정 여지(D40)는 F1 만 본 판단이다(세션 C): 사실 시트 보기에 '판단 기준'을 싣고, 7.3·8.2·8.3·9 지시문이 Recall 등 다른 지표 문제에
  '임계값 조정이 소용없다'고 적용하지 못하게 한다. 엔진이 조정 여지가 작다고 봤으면 8.3 에 임계값을 위험으로 쓰지 않게 한다.
- 최약 클래스 동점(세션 C, `required_items.weakest_ties`): 클래스별 표에서 F1 이 최약 클래스와 같은(인쇄 자릿수 넷째 자리 기준) 클래스가 더 있으면
  7.1-10·8.3-01 결론과 규칙 문장이 "F1 0으로 같은 두 클래스(2, 8)"처럼 함께 부르고(개수는 우리말 — 열 넘으면 '여러', 이름은 다섯까지),
  7.1·8.3 지시문이 하나만 단독 최약처럼 쓰지 못하게 한다. 표가 잘렸으면 '표에 실린 클래스 가운데'로 한정한다.
- 지표의 평균 방식(세션 C, `fact_view.averaging_text`): 사실 시트 보기의 지표 줄에 '평균 방식'을 싣는다 — 엔진에서 Precision·Recall·F1·F-beta 는
  이진이면 양성 클래스 기준, 다중·멀티레이블이면 매크로 평균, 멀티레이블 Jaccard 는 표본 평균. 다중·멀티레이블의 7.1·8.2·8.3 지시문은 매크로
  평균에 '평균에는 약한 클래스 부진이 드러나지 않는다'(가중·마이크로에만 맞는 말)를 쓰지 못하게 한다.
- 7.2 불균형 말투는 성적서 3절 불균형 진단과 같다(사용자 결정 2026-10-22): 엔진 판단이 '영향 있음'(affected)이면 결론·규칙 문장·지시문 모두
  "불균형에 따른 성능 지표 왜곡이 관찰되었다"로 쓰고, '불균형이 성능 수치에 영향을 주었다·준 것으로 보인다' 같은 인과 단정은 쓰지 않는다.
  소수 클래스의 크기는 세 상태다(`required_items.minority_size`): 작음(`facts.low_support_classes` 에 있음)이면 "표본이 적어 수치가
  흔들리기 쉬우니 해석에 유의", 작지 않음(목록이 온전한데 없음)이면 지시문이 '표본이 적은 클래스가 아니므로'를 싣고, 모름(facts 없음,
  `facts.omitted` 의 `low_support_classes`·`facts_class_lists`, 목록을 보내지 않음)이면 표본 크기를 단정하지 않고 '소수 쪽 해석에 유의'만
  싣는다. 규칙 문장은 작음일 때만 '표본이 적어', 그 밖은 "소수 클래스의 성능 지표 해석에 유의"(세션 C 재확인 실호출에서 64건 클래스에
  '표본이 적어'가 붙었다; 마지막 검토 — 모름을 작지 않음으로 단정했다). 덜 중요하게 보라는 뜻으로 읽히는 말('같은 무게로 읽지 않도록')을
  지시문이 막고, 의뢰자가 '모든 클래스가 동등'을 밝혔으면 그 선언도 지시문에 싣는다.
- 판정 문장 규칙(지시문 규칙 7): 미달한 지표가 있으면 그 미달이 종합 판정과 무관하다·영향이 없다고 쓰지 않는다(비핵심 미달은 조건부
  합격의 사유). 오류 성격 재료는 건수가 충분하고 우세한 쪽 하나가 과반이면 '주된 성격으로 해석해도 된다'를 함께 싣는다(합만 과반이면 합이 절반을 넘는다고만).
- 엔진 `success_metrics.imbalance_effect`(불균형 영향, D20)는 판정 세 값(`imbalance_ratio`·`accuracy_minus_macro_f1`·
  `majority_minus_minority_f1`, 표시는 판정 쪽으로 자릿수를 늘린 `judged_text`)과 함께 차이를 만든 네 값 `accuracy`·`macro_f1`
  (판정과 같은 정의 — 클래스별 F1 단순 평균; 멀티레이블은 둘 다 null)·`majority_f1`·`minority_f1` 를 싣는다. 네 값의 `display` 는 판정과
  무관해 엔진 평소 넷째 자리(`display.plain_text`). 성적서 3절 불균형 진단 문장의 재료이고, 사실 시트에 실리면 숫자 허용 목록에도 든다.

### 10.4 생성 흐름 (`generator.py`)

1. 장마다 한 번 — 7장(7.1·7.2·7.3)·8장(8.1·8.2·8.3)·9장(9)을 **동시에** 부른다. 문제 목록이 0개면 9장은 부르지 않는다(9칸은 규칙 문장, 출처 fixed).
   서술 지표 전부가 기준표에 없고 성적서가 고정 문구 16 을 찍으면(`required_items.benchmark_printed_only` — 참조 표가 비고, 비교 기준 없음
   항목 `8.1-03` 이 있고, `code_prints(…, "16")`) 8장 호출에서 8.1 만 뺀다(8.1 = 빈 글, 출처 fixed — 8.2·8.3 은 늘 있어 8장 호출은 남는다).
   8.1 을 부르지 않으니 빈 칸 검사는 그대로다(AI 가 쓴 빈 8.1 은 여전히 위반).
2. 모든 호출은 같은 사실 시트(AI 가 읽는 한국어 보기 — `fact_view.py`)와 결론 목록 전체를 받고 자기 장의 칸만 쓴다.
   다른 장 옆에 성적서가 숫자로 찍는 문장(17·18)은 "되풀이하지 않는다"로 알린다.
3. 호출 실패: 429(사용 한도)는 차례로 한 번 더, 호출 오류·시간 초과·JSON 오류는 한 번 더. 거절(refusal)·잘림(max_tokens)·모델 없음은
   **같은 요청으로 다시 부르지 않고** 그 장의 칸을 규칙 문장으로 — 거절된 요청은 약 1시간 동안 대체 모델로 고정 라우팅되기 때문이다.
4. 호출은 `llm.py` 한 곳: `client.beta.messages.create(model=claude-sonnet-5-5, betas=["server-side-fallback-2026-07-01"],
   fallbacks="default", max_tokens=16000, output_config={format: json_schema, effort})`, 비스트리밍, 온도·seed 없음.
   응답 스키마와 지시문에 추론 과정·근거 필드를 두지 않는다(그런 거절은 대체 모델이 없다).

### 10.5 칸별 검사와 검문 사다리 (`checks.py` · `grounding.py`)

| 검사 | 무엇을 | 걸리면 |
|---|---|---|
| ① 숫자 | 그 칸 글의 숫자가 모두 허용 목록 안(원본 사실 시트·파생값·고객 입력에서 만든 목록) | 그 칸만 1회 다시 → 또 걸리면 그 칸만 규칙 문장 |
| ② 판정 모순 | 판정과 어긋나는 단정(불합격인데 "모두 충족" 등 — 부정·조건·규칙 설명은 뺌) | 같음 |
| ③ 9칸 | 기대 효과의 예측 수치(지표값·향상폭 — '1차 원인'·'3개월 내'는 막지 않음. 숫자 꼴 클래스 이름 '클래스 2'·'2(…)'도 뒤에 건·개·칸·%·배나 개선 낱말이 붙지 않으면 막지 않음 — `checks.numeric_labels`), 권고가 빠진 문제 | 같음. 권고 하나만 빠졌으면 다시 만들고, 또 빠지면 그 문제만 종류별 권고 템플릿으로 채움 |
| ④ 선언 숫자(D24) | 의뢰자 선언이 있으면 그 숫자가 글에 있는가(7.1 위험 쪽 오류·8.2 선언 평균 방식·8.3 대화형 응답 시간) | 1회 다시 만들고, 그래도 없으면 **그대로 싣고 기록** |
| ⑤ 형식 | 빈 칸, 7.3 의 숫자 인용, 영어 판정 코드·밑줄 필드명 | ①과 같음(7.3 은 다시 만들지 않고 비움) |

- 한 칸의 HTTP 호출은 최대 2회(첫 장 호출이 재시도됐으면 그 칸은 다시 만들지 않는다). 숫자와 선언이 함께 걸려도 다시 만들기는 1회.
- 다시 만들기는 그 칸만 요청하는 호출이다(같은 사실·결론, 위반 숫자는 넣지 않음).
- 칸을 섞은 최종본에 판정 모순 검사를 한 번 더 한다(조립 결함 방어).
- 판정 모순 검사 전에 판정 낱말(미달·불합격 등)이 든 클래스 이름·고객 클래스 설명을 가린다(`checks.verdict_masks`) —
  '1(불합격품)' 을 부른 맞는 문장이 '미달했다'는 주장으로 읽히지 않게. facts 목록에만 남은 클래스 이름(잘린 표 밖)도 이름으로 본다.
- 시간: 작업 전체 10분 안에서 호출마다 남은 시간으로 제한을 줄인다. 남은 시간이 30초보다 적으면 부르지 않고 그 칸을 규칙 문장(사유 deadline).

### 10.6 규칙 템플릿 (`fallback.py`)

칸 함수 7개(`SECTION_TEMPLATES`)가 결론 목록의 템플릿 문장을 표 순서대로 잇는다. 결론 목록 밖의 문장은 칸의 앞뒤 사실 문장뿐이다
(7.1 혼동행렬이 없다는 말, 7.2 분포 나열, 8.1 기준의 출처, 8.3 목표 미달 위험, 9절 9.1·9.2 문장과 권고표). 옛 경로·키 없음은
일곱 칸을 모은 `build_fallback_narrative`, 작업 경로 사다리는 걸린 칸만 `section_template` 을 부른다.

- 작업 유형·고객 입력은 두 경로가 넘긴다. 넘기지 않은 옛 호출은 사실 시트로 짐작한다(`required_items.infer_task_type`).
- 클래스가 많아 프론트가 표를 잘랐으면(`facts.omitted`) 잘린 표에서 '가장 많은'·'전부'를 단정하지 않는다(실린 클래스 가운데로 한정).
- `facts` 가 없는 옛 요청(옛 프론트, 저장된 다시 만들기 요청)에서도 깨지지 않는다. 혼동행렬(M21)을 고르지 않아 행렬이 없으면
  엔진 클래스별 건수(`confusion_counts`)로 오분류 총건수를 센다(옛 요청만의 서버 셈 — 새 요청은 `facts.error_totals` 를 옮긴다).
- 검증(`tests/test_s6_templates.py`): 작업 유형 3 × 판정 4 가지로 템플릿 출력이 자기 검문(①②④⑤)을 통과, 17·18 숫자 묶음이 다시
  나오지 않음, 옛 경로 골든(`narrative_legacy_main_fallback` — 옛 경로 모양)과 새 골든(`narrative_job_fallback_*`)을 따로 둔다.

### 10.7 기록 둘과 작업 표 (`jobs.py` · `models.py`)

- **고객용**(조회 응답 `result`): 서술 본문 + 칸별 출처(`section_sources` — `llm` · `fallback`(규칙 문장으로 대체) · `fixed`(고정 문구))
  + 칸별 모델 이름(`section_models` — 키는 일곱 칸 전부, `llm` 칸만 그 글을 낸 호출의 응답 모델이고 `fallback`·`fixed` 는 null. 다시 만든
  글이면 다시 만든 호출, 첫 글을 둬 뒀다 실으면 첫 호출의 모델. 작업 행 상한으로 바로 규칙 문장인 경우도 전부 null). 성적서 화면의 '작성
  기록'에 쓰인다(사용자 결정 2026-10-22 — 그 전에는 모델을 내부용에만 뒀다). 번호만 알면 열리므로 이것만 싣는다.
- **내부용**(`internal_json`, 서버 로그): 실패 종류, 칸마다 출처·결과(first·second·kept_first·filled·template·dropped·fixed)·시도 수·
  검사 기록, 호출마다 목적·칸·응답 모델(대체 모델 포함)·대체 요청을 보냈는지·거절 종류·토큰·비용·슬롯 대기, 429 횟수, 단계별 시각,
  7.3 원문. 입력(사실 시트·고객 입력)은 저장하지 않는다 — 작업은 메모리의 요청으로 돌고, 서버가 재시작되면 유실이 된다.
- 표 `narrative_jobs`: `status`(running·done·failed) · `stage`(queued·generating·checking·regenerating·done·failed) · `result_json` ·
  `internal_json` · `created_at`/`updated_at`/`finished_at`(tz 없는 UTC). **열은 확정** — 앞으로는 두 JSON 칸 안에서만 늘린다(§7 규칙 4).
- 끝나는 방식: 서술이 생기면 AI 든 규칙 문장이든 **완료**(키 없음·지갑 소진·호출 실패·검사 위반·입력 상한 초과 모두). **실패**는 전체 10분
  초과(timeout)·멈춤(lost — 마지막 갱신 뒤 360초 또는 만든 뒤 630초, 조회 때 판정)·예기치 않은 오류(error)·결과 글을 지움(expired).
- 장별 호출이 동시에 단계를 쓰므로 단계 쓰기는 하나씩(`asyncio.Lock` — SQLite 는 연결 하나를 스레드끼리 같이 쓰면 깨진다).
- **Postgres 왕복**(로컬): `docker run -d --name <이름> -e POSTGRES_PASSWORD=<비번> -p 127.0.0.1:55433:5432 postgres:17-alpine` 뒤
  `NARRATIVE_PG_URL=postgresql://postgres:<비번>@127.0.0.1:55433/postgres venv/bin/python -m pytest tests/test_postgres_roundtrip.py`.
  작업 생성 → 장 셋 동시 단계 쓰기 → 완료 → 조회, 라우트 왕복, 유실·만료 판정을 본다. CI 에서는 건너뛴다.

### 10.9 결정 번호 색인 (코드 주석의 "서술 설계 Dnn")

코드 주석이 인용하는 서술 설계 결정의 뜻을 여기 옮겨 둔다(원문 없이 읽히게). `D3a`·`D7[1]` 처럼 글자·대괄호가 붙은 번호는 2026-06 서술 모듈
첫 구현 때의 결정 번호로, 서술 설계 번호와 다르다(아래 둘째 표).

| 번호 | 뜻 |
|---|---|
| D2 | 성적서 절 구조는 예시본을 따른다(7.3 만 추가). 절 안의 내용은 필수 서술 항목 목록이 정한다 |
| D6 | 파생값(마진·최약 클래스·최다 오분류 쌍·예측 편향·판정 근거)은 코드가 계산해 표로 찍고, AI 가 같은 값을 문장으로도 쓴다 |
| D7 | AI 에 코드가 뽑은 결론 목록과 숫자 시트를 함께 준다. 결론은 반드시 문장으로, 시트에서 더 찾은 것은 "추가 관찰"로 구분(숫자 인용 필수) |
| D12 | 기준값: 작은 표본 30건 미만 또는 5% 미만, Precision↔Recall 차 0.10, 근소 차이 = 목표값과의 차이가 목표값의 3% 미만 |
| D17·D39 | 클래스별 표의 평균 줄(매크로·가중, 멀티레이블은 매크로·마이크로)을 시트에 싣고 8.2 에 평균 방식 차이를 쓴다 |
| D19 | 판정 규칙: 핵심 지표 하나라도 미달 → 불합격, 핵심 지표 산출 실패·판정 대상 0개 → 판정 불가, 핵심은 충족·그 외 미달 → 조건부 합격, 전부 충족 → 합격. 통과율은 참고 수치 |
| D20 | 불균형 영향: 불균형 비율 1.5 이상이고 (정확도 − 매크로 F1) 또는 (다수 − 소수 F1)이 0.10 이상이면 영향 있음, 둘 다 미만이면 왜곡 없음, 1.5 미만이면 경미. 판정은 평가 엔진 한 곳 |

| D24 | 의뢰자 선언 3개(위험 방향·클래스 중요도·사용 방식)의 숫자가 빠지지 않게 네 장치: 허용 목록, 지시문 강조, 필수 항목, 생성 뒤 확인(없으면 1회 다시, 그래도 없으면 그대로 싣고 기록). "특별한 것 없음"이면 끈다 |
| D25·D34 | 고객 입력은 AI 에 넘겨 자유롭게 쓴다. 식별 정보는 모델명·버전만(회사·과제 정보는 넘기지 않는다) |
| D28 | 다중 클래스 평균 방식은 클래스 중요도 선언에 맞춘다(동등 = 매크로, 다수 우선 = 가중, 샘플 단위 = 마이크로) |
| D29 | 통계적 유의성 검정 대신 판정 대상 지표의 95% 신뢰구간을 계산해 서술 재료·허용 목록에 넣는다 |

### 10.10 왜 이렇게 만들었나 — 처음 설계 때 정한 것 중 지금도 그대로인 것

- **AI 는 숫자를 만드는 쪽이 아니라 옮기는 쪽이다.** 모든 숫자는 평가 엔진(`app/evaluation/`)과 서버 파생 계산이 정하고,
  AI 는 그 값을 한국어 문장으로 옮기기만 한다. 그래서 숫자 검문(§10.5 ①)이 "허용 목록 밖 숫자 = 지어낸 숫자"로 볼 수 있다.
- **평가(`/api/evaluate`)와 서술(`/api/narrative/jobs`)은 따로 부른다.** 서술 AI 가 실패해도 지표 계산이 500 이 되지 않고,
  지표·차트는 바로 보이며 서술만 뒤에 온다. 다시 만들 때도 원본 CSV 를 다시 올리지 않고 사실 시트(수 KB)만 보낸다.
- **판정(verdict)은 프론트 `src/lib/report/computeVerdict.ts` 가 규칙으로 계산한다**(AI 가 정하지 않는다). 백엔드는 사실 시트에
  실려 온 판정을 그대로 쓴다. 판정 대상은 **목표값이 있고 산출에 성공한 지표만**이다(혼동행렬 같은 정보 제공 지표는 빠진다).
  핵심 지표(미달이면 불합격)의 기본값은 유형별로 이진·다중 클래스 = Accuracy(M1)·F1(M4, 다중은 매크로),
  멀티레이블 = F1(M4)·Jaccard(M17)이고, 사용자가 합격 기준 화면에서 바꿀 수 있다. 판정 규칙 네 단계는 §10.9 D19.
- **8.1 벤치마크는 고정된 참조 표(`app/narrative/baselines.py`)로 비교한다 — 웹·벡터 DB 검색(동적 RAG)은 쓰지 않는다.**
  검색 결과는 실행마다 달라져 같은 성적서를 다시 만들 수 없고, 출처를 확인할 수 없는 숫자가 성적서에 들어갈 수 있기 때문이다.
  표의 범위는 공개 벤치마크 평균이 아니라 내부에서 정한 보수적인 기준이라 **"내부 참조 기준치"** 라고 부르고, 출처 문구
  (`SOURCE_NOTE`)를 함께 싣는다 — 권위 있는 외부 기준처럼 보이지 않게. 모델 값이 범위의 아래·안·위 어디인지는 서버가 계산하고
  (AI 는 위치를 문장으로 옮길 뿐), 표에 없는 지표는 비교하지 않는다(고정 문구 16). 나중에 실제 도메인 기준으로 바꾸려면
  `get_baseline()` 한 곳만 바꾸면 된다.

## 11. 발급(issuance) — 성적서 번호·정정 발급·보관본

한 줄 요약: **번호는 '발급' 버튼을 누를 때 받는다. 같은 평가(run)는 몇 번 눌러도 번호가 하나이고, 고칠 때는 번호를 그대로 두고 차수만 올린다.**

- **번호 규칙**: `RPT-{연도}-{순번 4자리}`(예: `RPT-2026-0001`). 순번은 해마다 1 부터 다시 센다. 연도는 한국 시간(KST) 기준이다 —
  UTC 연도를 쓰면 1월 1일 오전(KST)에 발급한 문서가 번호는 전년도, 발급일은 새해가 된다.
- **번호를 받는 때**: 평가가 끝났을 때가 아니라 사용자가 **발급**할 때다. 평가만 하고 버린 run 에 번호를 낭비하지 않고, 번호가 있으면
  발급본, 없으면 초안이라는 뜻이 분명해진다.
- **같은 run = 같은 발급(멱등)**: `POST /api/reports/issue` 를 같은 `run_id` 로 다시 부르면 새 번호 없이 기존 발급본을 돌려준다.
  `report.run_id` 에 UNIQUE 제약이 있어 동시에 두 번 눌러도 번호가 둘 생기지 않는다.
- **정정 발급**: `POST /api/reports/{no}/reissue` 는 번호를 그대로 두고 차수를 올린다(`v1.0` → `v1.1` → `v1.2`). 이전 차수 행은
  `superseded`(대체됨)로 바뀌고 새 차수가 `issued` 다. 요청에는 `run_id` 가 꼭 있어야 하고, 그 성적서의 run 과 다르면 거절한다(번호는
  차례로 셀 수 있지만 run_id 는 추측할 수 없어서, 번호만 아는 제3자가 남의 성적서를 정정하지 못한다).
- **동시에 발급할 때**: `UNIQUE(year, seq)` 와 `UNIQUE(report_id, version)` 제약이 같은 번호·같은 차수가 두 번 저장되는 것을 막고,
  부딪히면 되돌린 뒤 다시 계산해 **최대 5번** 다시 시도한다(`service.py` `_MAX_NUMBERING_RETRIES`). SQLite 에서는 트랜잭션을
  `BEGIN IMMEDIATE` 로 열어 쓰기를 한 줄로 세운다(PostgreSQL 에는 적용되지 않음 — 제약 + 재시도가 방어선, §8.2 F-12).
- **기관(organization)은 한 행뿐**(id=1). 기동 때 표가 비어 있으면 기본 기관("리트머스")을 넣는다(`bootstrap.py`). 기관을 바꾸는
  API(`PUT /api/organization`)는 **일부러 두지 않는다** — 인증이 없는 상태에서 누구나 이미 발급한 성적서의 기관 표기를 바꿀 수
  있었기 때문이다. 바꿀 때는 §12 처럼 DB 에서 한 번 직접 바꾼다.
- **발급 시점 보관본**: 차수마다 `report_snapshot` 한 행에 그때의 기관 정보(`org_snapshot_json`)와, 프론트가 보낸 성적서 원본
  (`content_json`, 선택, 1 MiB 상한)과 그 SHA-256 을 저장한다. 그래서 나중에 기관 이름을 바꿔도 이미 발급한 성적서의 표기는
  그대로다. 보관본이 없는 옛 발급본은 현재 기관 행으로 보여 준다(없던 사실을 소급해 만들어 넣지 않는다).
  원본은 `GET /api/reports/{no}/content`(`?version=v1.0` 으로 이전 차수)로 다시 받는다. 발급 이력에는 직전 차수와 비교해 값이
  바뀐 최상위 절 목록이 붙는다.
- **시각**: DB 에는 tz 없는 UTC 로 저장하고, 응답의 `issued_at` 은 `+00:00` 오프셋을 붙인 ISO8601 로 내보낸다. 오프셋이 없으면
  프론트가 한국 시간으로 잘못 읽어 날짜가 하루 어긋날 수 있다. 화면 표기(KST)는 프론트가 한다.
- **가짜 데이터 0**: 발급 전 성적서는 가짜 번호를 만들지 않고 "초안(미발급)"으로 표시한다(프론트). 서버도 모르는 값은 지어내지 않는다.
- **표**: `organization`(기관 1행) 1 : N `report`(번호 단위) 1 : N `issuance`(차수 이력), `report` 1 : N `report_snapshot`(차수별 보관본).
  서술 작업 표 `narrative_jobs` 는 발급과 관계없는 따로 선 표다(§10.7). 다섯 표 모두 기동 때 `init_db()` 의 `create_all` 이 만든다.

## 12. 배포·운영

한 줄 요약: **팀 저장소 main 에 push → CI 통과 → 포크로 복사 → Render 가 빌드. 되돌릴 때는 Render 의 Rollback 이 아니라 되돌리는 커밋으로.**

| 구분 | 실제 값 |
|---|---|
| 백엔드 | Render 무료 web service — `https://capstone-back-59z8.onrender.com` |
| 프론트 | Vercel — `https://capstone-beta-lilac.vercel.app`. 빌드 때 `VITE_API_BASE_URL` 로 Render 주소를 넣고, 브라우저가 백엔드를 **직접** 부른다(Vercel 프록시는 응답을 약 30초에 끊어 콜드 스타트·긴 LLM 응답에서 실패한다) |
| DB | Neon PostgreSQL(무료, 연결 문자열은 Direct connection). Render 무료 Postgres 는 30일 뒤 만료되고, Supabase 무료는 7일 쉬면 일시 정지돼 손으로 살려야 해서 Neon 을 골랐다 |

**배포 경로**

1. 팀 저장소(`hwanginyong02/Capstone_Back`) `main` 에 push.
2. CI(`.github/workflows/ci.yml`)의 test job — `pytest -q` 뒤 실제로 서버를 띄워 스모크: `/health` → `/api/organization` →
   발급 → 발급정보 조회 → `/content` 원본 조회 왕복 → 서술 작업 `POST /api/narrative/jobs` → `GET` 이 `done` 이 될 때까지 보고,
   칸 출처가 `fallback`·`fixed` 뿐인지(키 없는 CI 라 AI 칸이 없어야 함) 확인.
3. deploy job — 포크 `hellinii/Capstone_Back` 의 `main` 으로 그대로 복사(force push) → Render Deploy Hook 호출 →
   `/health` 의 `commit` 이 방금 커밋과 같아질 때까지 최대 15분 기다리고, `persistent:true`(영속 DB)인지도 본다.

Render 는 포크 main 을 따라가지만 자동 배포가 꺼져 있어(`autoDeploy: false`) Deploy Hook 이 유일한 배포 길이다.
`render.yaml` 은 **참고용**이다 — 이 서비스는 대시보드에서 직접 만든 것이라 Start Command·환경변수 등은 대시보드 값이 정본이다.

**운영 메모**

- **Rollback 금지(2026-10-23 부터)**: Render 대시보드의 Rollback 으로 옛 리비전을 띄우면 그 리비전은 종료된 옛 모델을 부른다.
  문제가 생기면 되돌리는 커밋(revert)을 만들어 같은 배포 경로로 내보낸다.
- **환경변수(Render 대시보드 Environment)**: `DATABASE_URL`(Neon), `OPENAI_API_KEY`(매핑), `ANTHROPIC_API_KEY`(서술), `PYTHON_VERSION`.
  서술만 문제가 생기면 `ANTHROPIC_API_KEY` 를 지워 규칙 문장으로 돌린다. 키가 들어 있는지·어떤 모델인지는 `/health` 의
  `llm.narrative`·`llm.mapping`(`key`·`model`)으로 본다. 환경변수를 저장해도 서버가 다시 뜨지 않을 수 있으니 **Manual Deploy** 로 다시 띄운다.
- **기관 이름 바꾸기**: API 가 없으므로(§11) Neon SQL 편집기에서 한 번 직접 바꾼다 — 예:
  `UPDATE organization SET org_name = '리트머스' WHERE id = 1;`(운영 DB 에는 2026-10-23 에 이미 적용). 이미 발급한 성적서의
  `issuance.issuer`(발급 당시 발급자 문자열)와 보관본은 바꾸지 않는다 — 발급 당시 그대로가 맞다.
- **새 표**: `narrative_jobs` 처럼 새 표는 기동 때 `create_all` 이 알아서 만든다. 이미 있는 표에 열을 더하는 것은 하지 못하므로
  (마이그레이션 도구 없음, §7 규칙 4) 스키마를 늘릴 때는 새 표로 한다.
- **콜드 스타트**: Render 무료는 한동안 요청이 없으면 잠들고, 깨어나는 데 30~60초쯤 걸린다. 시연 전에 `/health` 를 한 번 불러 깨운다.
- **Neon 연결 문자열**: `sslmode=require` 를 둔다. 연결 때 `channel_binding` 옵션 오류가 나면 그 옵션만 빼면 된다.
