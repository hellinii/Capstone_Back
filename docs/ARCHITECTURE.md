# 백엔드 구조 한눈에 보기 (처음 오신 분 먼저 읽기)

이 문서 하나면 **5분 안에** 이 백엔드가 뭘 하고, 코드가 어디 있고, 새 작업을 어디서 시작할지 알 수 있습니다. 코드를 처음 연다는 가정으로 씁니다.

---

## 1. 이 백엔드가 하는 일 (한 문단)

**ISO/IEC TS 4213** 기준으로 AI **분류 모델**의 성능을 평가하고 성적서를 발급하는 FastAPI 서버입니다. 사용자가 모델 예측 결과 파일(CSV/JSON)을 올리면 → ① **어떤 컬럼이 정답/예측/점수인지 파악**하고(LLM 자동 매핑, OpenAI) → ② **지표(정확도·정밀도 등)를 계산**하고 → ③ **결과를 자연어로 설명**하고(성적서 7·8·9절, Claude — 판 4 성적서는 다른 모델(OpenAI)이 그 설명을 데이터와 맞대 검사하는 심판을 거친다, §14) → ④ **성적서를 발급**합니다. Render + Neon Postgres에 배포됩니다(§12).

## 2. 딱 한 장으로 보는 구조

> **핵심 규칙 하나만 기억하세요: `app/` 아래 폴더 = "하는 일(도메인)" 하나.**
> 그리고 **어느 도메인이든 파일 구성이 똑같습니다** → `router`(API) → `service`(흐름 조율) → 나머지(세부 로직) + `schemas`(그 도메인의 데이터 형태).

```
app/
├── main.py            앱 진입점 (uvicorn app.main:app) — 라우터 5개 연결, 시작 시 DB 준비
│
├── core/              🔧 모든 도메인이 공유하는 것
│   ├── schemas.py       공용 데이터 규격(enum·역할규칙·지표요건·"분석→평가" 인계 모델)
│   ├── database.py      DB 연결(SQLAlchemy) — 로컬 SQLite / 배포 Postgres
│   ├── parsing.py       업로드 파일(CSV/JSON) → 표(DataFrame) 변환 (공용 유틸)
│   ├── upload.py        업로드 경계 검사(확장자·크기 20 MiB·빈 파일) — 업로드 라우터 셋이 같이 씀
│   ├── concurrency.py   무거운 계산을 스레드풀로 넘기고 동시 실행 수를 묶음(이벤트 루프가 멈추지 않게)
│   └── llm_budget.py    LLM 호출의 시간당 총량 상한(넘으면 규칙 폴백, 429 아님)

│   ├── router.py            API: 컬럼 매핑 (/api/analyze-columns, /api/confirm-mapping)
│   ├── validation_router.py API: 데이터 검증 (/api/validate-data)
│   ├── analysis_service.py    흐름 조율(무키면 규칙매핑, LLM 실패하면 규칙매핑으로 강등)
│   ├── validation_service.py  데이터 검증 흐름 조율

│   ├── prompt_builder.py 매핑용 LLM 프롬프트          validator.py  매핑 유효성·계산가능 지표
│   ├── validation_checks.py  데이터 점검 항목들       schemas.py  이 도메인 데이터 형태
│
├── evaluation/        ② 평가 — 지표 계산
│   ├── router.py        API (/api/evaluate)          service.py  평가 흐름 조율
│   ├── engine.py        지표 → 계산함수로 분배          preprocessor.py  계산 전 데이터 정리
│   ├── report.py        결과 성공/실패 정리           schemas.py
│   ├── frame.py         평가에 들어갈 행을 정하는 규칙 한 곳   labels.py  클래스 표기·양성 기본값(§9.2·§9.4)
│   ├── errors.py        지표 계산 실패 표시 키 한 곳   environment.py  평가 환경(도구 버전·일시) 실측 + 평가 엔진 버전 ENGINE_VERSION(§13)
│   └── metrics/         실제 지표 계산(sklearn): common·binary·multiclass·multilabel
│                        + counts(TP·FP 등 건수) · intervals(95% 신뢰구간) · misclassification(경계·확신 오류)
```

(`dev_fake_llm_server.py`). §14.9·§14.10.

DB 표는 모두 5개다 — 발급 4개(`organization`·`report`·`report_snapshot`·`issuance`, `issuance/models.py`)와 서술 작업 1개(`narrative_jobs`, `narrative/models.py` 의 `NarrativeJob`). 자세히는 §11.

> 💡 각 폴더의 `__init__.py`에는 그 도메인의 **파일 목차** 주석이 있습니다(나중에 생긴 파일이 빠져 있을 수 있으니 실제 목록은 위 나무를 보세요). 각 `.py` 파일 맨 위에는 **"이 파일이 뭐고 뭐랑 상호작용하는지"** 헤더 주석이 있습니다.

## 3. 요청이 흐르는 순서

사용자가 파일을 올리면 도메인을 **순서대로** 거칩니다. 이 흐름 = 위 폴더 순서입니다.

```
[예측결과 파일 업로드]
      │
      ▼
① /api/analyze-columns   analysis : 컬럼 역할 자동 파악 (LLM, 없으면 규칙)
      ▼
① /api/confirm-mapping   analysis : 사용자가 고른 매핑 검사 → 계산 가능한 지표 목록
      ▼  (선택) /api/validate-data  analysis : 계산 전 데이터 점검(결측·중복 등)
      ▼
② /api/evaluate          evaluation : 지표 계산
      ▼
③ POST /api/narrative/jobs narrative : 작업 번호 + 8.1 벤치마크 표를 바로 돌려주고, 서술은 뒤에서 만든다
③ GET  /api/narrative/jobs/{id}      : 단계(대기·생성 중·검사 중·다시 만드는 중·검증 중(판 4)·완료·실패)와 결과
      │    (판 4 작업은 서술을 만든 뒤 심판이 검사한다 — 통과해야 발급 가능, 아니면 발급 보류. §14)
      │    (옛 경로 /api/generate-narrative 는 옛 클라이언트용으로 얼려 둠 — 운영 프론트는 2026-10-23 배포부터
      │     작업 경로만 쓴다. 다음 라운드에 지운다)
      ▼
④ /api/reports/issue     issuance : 성적서 번호 발급 + DB 저장(판 4 성적서는 심판 통과 작업 번호 검사, §14.6)
   (발급 뒤 GET /api/reports/{no} 발급정보 · GET /api/reports/{no}/content 발급 시점 원본 · POST /api/reports/{no}/reissue 정정 발급)
```

- **LLM 을 쓰는 곳**: ①분석은 OpenAI(`OPENAI_API_KEY`, 모델 `MAPPING_MODEL` 기본 `gpt-6-luna`), ③서술은 Anthropic(`ANTHROPIC_API_KEY`, 모델 `NARRATIVE_MODEL` 기본 `claude-sonnet-5-5`), ③'판 4 심판은 OpenAI(같은 `OPENAI_API_KEY`, 모델 `JUDGE_MODEL` 기본 `gpt-6.1-sol` — §14.11). 키가 없거나 호출이 실패하면 자동으로 규칙 기반으로 대체돼서 서버는 안 죽습니다(판 4 는 심판을 못 하면 서술은 보이되 발급 보류).
- **DB를 쓰는 곳**: ④발급 표와 ③서술 작업 표(`narrative_jobs` — 진행 단계·결과·내부 기록, 입력은 저장하지 않음). 나머지는 업로드 파일을 메모리에서 처리하고 끝(디스크 저장 없음).

## 4. 도메인 요약표

| 도메인 | 하는 일 | 주요 API | "진입점" 파일 |
|---|---|---|---|
| **core** | 공용 규격·DB·파일파싱 | — | `schemas.py`, `database.py` |
| **analysis** | 컬럼 파악 + 데이터 점검 | `/api/analyze-columns`, `/api/confirm-mapping`, `/api/validate-data` | `router.py` → `analysis_service.py` |
| **evaluation** | 지표 계산 | `/api/evaluate` | `router.py` → `service.py` |
| **narrative** | 결과 서술 | `/api/narrative/jobs`(새) · `/api/generate-narrative`(옛) | `router.py` → `jobs.py` → `generator.py` (옛 경로는 `legacy.py`) |

시스템: `GET /health` (상태 확인).

## 5. 새 작업을 어디서 시작하나 (신규 개발자용)

| 하고 싶은 것 | 열 파일 |
|---|---|
| API 동작/입출력 바꾸기 | 해당 도메인 `router.py` (얇음 — 검증·상태코드만) |
| 비즈니스 로직(흐름) 바꾸기 | 해당 도메인 `service.py` (서술은 `jobs.py`·`generator.py`, 옛 경로 `legacy.py`) |
| 요청/응답 필드 추가 | 해당 도메인 `schemas.py` (공용이면 `core/schemas.py`) |
| 새 지표 추가 | `evaluation/metrics/*` + `evaluation/engine.py`의 레지스트리 |
| 서술에 꼭 쓸 내용(항목·결론) | `narrative/required_items.py` — AI 지시문과 규칙 템플릿이 같이 읽는다(§10.3) |
| 서술 지시문 / 규칙 문장 | `narrative/prompt.py`(AI) / `narrative/fallback.py`(규칙 템플릿 — 칸 함수) |
| 서술 검사(숫자·판정 모순 등) | `narrative/checks.py`, `narrative/grounding.py` |
| DB 테이블 | `issuance/models.py`, `narrative/models.py` |
| 판 4 심판이 재는 것(항목·규칙·프롬프트) | `judge/criteria/` — 고치면 MANIFEST 다시 쓰기·버전·재검증(§14.7) |
| 판 4 보류 종류·다시 만들기 허용 | `judge/ladder.py` 의 `held_kind`·`retry_allowed`(§14.4) |
| 판 4 발급 거절 사유 | `issuance/judge_gate.py`(§14.6) |

**패턴이 거의 같습니다**: 요청은 `router`(HTTP만) → `service`(흐름) → 세부 헬퍼로 흐릅니다. 예외는 서술(narrative)로, 흐름이 `jobs.py`(작업 번호) → `generator.py`(장별 생성·칸별 검문)와 옛 경로 `legacy.py` 에 있습니다(§10).


> 테스트는 `venv/bin/python -m pytest` 로 돌린다(zsh 에서는 `source venv/bin/activate` 가 듣지 않을 수 있다).

## 7. 알아두면 좋은 규칙

1. **import는 절대 경로** (`from app.analysis.llm_mapper import ...`).
2. **의존 방향은 항상 도메인 → core** (core는 도메인을 모름 → 순환 없음). 예외: 평가가 분석의 파싱/검증을 재사용(상류 참조)하는 것은 허용.
3. **`app/__init__.py`·`app/core/__init__.py`에 `import`를 넣지 마세요** — `main.py`의 `load_dotenv()`가 DB import보다 먼저 실행돼야 하는 순서가 깨집니다(파일 주석 참조).
4. **DB 스키마는 `init_db()`의 `create_all`로 생성**(마이그레이션 도구 없음).
5. 배포 구성은 §12(배포·운영) 참조.

> 항목 번호다. 대장 자체는 저장소에 없고, 번호는 "언제 무슨 문제로 바뀐 코드인가"를 알려 주는 이력 표시로만 남겨 둔다.
> 뜻은 그 자리의 설명을 읽으면 된다.

### 8.1 성적서의 진본성 — 서버가 완전히 보증하지는 않는다 (F-02·F-03·F-05)

발급 시점의 성적서 원본(JSON + SHA-256)과 기관 스냅샷은 서버에 보관된다. 번호로
복원할 수도 있다. 그러나 **다음 셋은 구현하지 않았다.**

| # | 한계 | 왜 이번 범위에서 제외했나 |
|---|---|---|
| **F-02** | 평가와 발급이 서버에서 결속되지 않는다 — 평가를 거치지 않고도 정식 번호를 받을 수 있다 | 백엔드 단독으로 닫히지 않는다(프론트 필수·3단 롤아웃). 무엇보다 **기존 사용자 전원이 발급 불가**가 되고, 결속을 넣어도 **2행짜리 CSV 로 평가를 통과시켜 우회**할 수 있어 실효가 낮다 |
| **F-03** | 서술 API 가 클라이언트가 보낸 `fact_sheet` 를 다시 계산해 대조하지 않고 그대로 믿는다 — 작업 경로 `POST /api/narrative/jobs` 도 옛 경로 `/api/generate-narrative` 도 같다(형식·길이 상한 검사만 한다) | F-02 와 같은 뿌리다. 서버가 평가 결과를 갖고 있어야 대조할 수 있는데 그것이 F-02 다 — 따로 닫으면 반쪽이 된다 |

### 9.1 규칙 폴백 매퍼 (OpenAI 키가 없거나 LLM 이 실패할 때)

`app/analysis/fallback_mapper.py` 의 `fallback_role` 이 컬럼 **이름만** 보고 역할을 고른다. 이름은 낱말로 쪼갠다 —
구분자(`_` `-` 공백 `.`)와 camelCase 경계(`imageId` → image, id). 순서대로 보고 처음 맞는 것을 쓴다.

1. 정답 이름(`y_true`·`label`·`target`·`ground_truth`·`actual`·`true_label(s)` …) → `y_true`(멀티레이블은 `true_labels`)
2. 예측 이름(`y_pred`·`pred`·`prediction`·`predicted`·`pred_label(s)` …) → `y_pred`(멀티레이블은 `pred_labels`)
3. 지연시간 이름(`latency`·`latency_ms`·`inference_time(_ms)`·`response_time(_ms)`·`elapsed_ms`, 또는 낱말 `latency`) → `latency`
4. 낱말 `id`·`idx`·`index`·`uid`·`uuid`, 또는 붙여 쓴 식별자 이름(`sampleid`·`rowid`·`userid`·`fileid` 등 목록) → `sample_id`. `valid_flag`·`width` 처럼 'id' 가 **들어 있기만** 한 이름은 잡지 않는다
5. 낱말 `prob`·`proba`·`probability`·`score`(복수형·숫자 꼬리 `probs`·`scores`·`prob1` 포함), 또는 `p_` 로 시작 → 유형의 확률 역할(`score_positive`·`prob_per_class`·`score_per_label`). 이진은 낱말 `positive` 도. `position` 같은 이름은 잡지 않는다
6. 그 밖은 `ignore` + "규칙으로 판단하지 못했다" 안내

한 컬럼만 받는 역할(샘플 ID·정답·예측·이진 확률·지연시간)을 두 번째 컬럼이 또 잡으면, 첫 컬럼만 그 역할로 두고
나머지는 `ignore` 로 내린 뒤 `column_notes` 에 `status="duplicate_role"` 안내를 싣는다 — 역할이 겹치면 매핑 확정이
막히기 때문이다. 단 이진에서 양성 확률 후보가 여럿(`prob_0`·`prob_1`)이면 기본 양성 클래스(§9.2)
이름이 붙은 컬럼을 남긴다 — 첫 컬럼을 남기면 음성 확률이 양성 확률로 들어가 AUROC 가 조용히 뒤집힌다. 이름이 맞는
후보가 없으면 첫 컬럼. 확률 역할은 클래스·레이블마다 한 컬럼이라 여러 컬럼을 그대로 받는다.

자동 매핑 AI 지시문(`app/analysis/prompt_builder.py`)도 다중·멀티 확률 컬럼을 확률 역할로 안내한다(종전에는
"확률 컬럼도 ignore"라고 적어 y_pred 없는 파일의 예측이 사라졌다). 지시문의 역할 집합은 `VALID_ROLES_BY_TASK` 와 같다.

### 9.2 양성 클래스 기본값

사용자가 양성 클래스를 고르지 않았을 때의 기본값은 `app/evaluation/labels.py` `default_positive_class` 하나에서 정한다.
자동 판단(`analysis/metadata.py`)·지표 계산·확률에서 예측 파생(`preprocessor.py`)이 모두 이 함수를 쓴다. 지표 계산은
`metrics/binary.py` 의 `_resolve_positive_value` 한 곳에서 양성을 정하고, Precision·Recall·F1(`metrics/common.py`
`_get_binary_kwargs`)·신뢰구간·혼동 수 집계도 그 함수를 부른다. 양성이 지정되면 그 표기의 원래 값(§9.4)을, 지정되지
않으면(metadata 없이 API 를 직접 부른 경우) 이 기본값을 쓴다.

1. 숫자면 큰 값(1 > 0)
2. 알려진 짝(yes/no·true/false·positive/negative·spam/ham·malignant/benign·fraud/normal …)이면 정해진 값
3. 그 밖은 정렬 순서(숫자면 수치 순, 아니면 사전 순)의 **뒤쪽** 값 — 임시로 고른 것이라 `positive_class_ambiguous=true` 로 알린다

종전에는 3번에서 자동 판단만 **앞쪽**을 골라 화면에 보인 양성과 성적서 수치의 양성이 달랐다('cat'·'dog' 이면 화면은
cat, 지표는 dog). 이제 셋 다 dog 다. 지난 평가는 저장된 양성 값을 쓰므로 영향이 없다. 양성 미지정일 때
Precision·Recall·F1 만 정렬 뒤쪽 값을 쓰던 예외도 없앴다(fraud/normal 이면 종전엔 그 셋만 normal 을 양성으로 봤다).
프론트는 양성을 늘 보내므로 화면 결과는 바뀌지 않는다.

### 9.3 검증 단계에서 미리 보는 것 (`/api/validate-data`)

- **확률 컬럼 이름**(`Probability column names`, error): 다중·멀티에서 예측 컬럼 없이 확률만 매핑하고, 고른 지표가 예측을
  쓰면 평가는 확률 컬럼 이름으로 클래스를 확정해 예측을 만든다. 이름으로 확정할 수 없으면(예: 클래스가 cat/dog 인데
  컬럼이 prob_a·prob_b) 종전에는 검증을 통과한 뒤 평가에서 400 으로 막혔다. 이제 평가와 **같은 함수**
  (`preprocessor.derivation_source`·`probability_names_problem`)로 검증이 미리 보고 막는다. 예측 컬럼이 있거나 이름이
  맞으면 항목을 내지 않는다. 이진은 확률 컬럼이 하나라 이름을 보지 않는다.
- **지연시간 단위**(`Latency unit`, warning): 지연시간 역할은 ms 로 읽는다. 값이 모두 1 미만이면 초로 적은 것으로 보여
  경고한다. 1 ms 미만으로 도는 모델도 있어 막지 않는다 — 단위는 데이터만으로 확정할 수 없다.
- **이진 클래스 수**(`Binary class system error`): 정답∪예측 클래스가 둘을 넘으면 error(평가도 400 으로 멈춘다 —
  `preprocessor._check_binary_classes`). 정답 클래스가 하나뿐이면 예측에 두 클래스가 있어도 warning(`found 1`, 평가는 계속).

### 9.4 클래스 표기

데이터의 클래스 값과 화면·API 가 주고받는 클래스 이름은 다를 수 있다. 빈 칸이 하나라도 있으면 pandas 가 정수 정답
컬럼을 float 로 읽어 1 이 1.0 이 되고, 문자열 클래스에는 앞뒤 공백(`' cat'`)이 붙어 있을 수 있다.

- **주고받는 이름은 표기 하나**: `app/evaluation/labels.py` `normalize_label` — 정수 값 float 는 소수점 없이(1.0 → `'1'`),
  앞뒤 공백은 뗀다(`' cat'` → `'cat'`). metadata 의 클래스 목록·`positive_class`, 응답의 `derived_prediction.positive_class`·
  `negative_class`, `confusion_counts.positive_class` 가 모두 이 표기다. 그래서 정답이 float 이면 양성은 `'1.0'` 이 아니라
  `'1'` 로 나간다(정수·문자열 정답은 종전과 같다). 이미 저장된 옛 run 의 metadata 에는 `'1.0'` 이 남아 있을 수 있다.
- **원래 값은 `find_label` 로 되찾는다**: `y_true == 양성` 처럼 데이터 값과 비교하는 곳은 `str()` 로 맞춰 보지 않고
  `labels.find_label(값들, 표기)` 로 원래 값(1.0·`' cat'`)을 찾아 쓴다. 쓰는 곳: 이진 예측 파생(`preprocessor.py`),
  `binary._resolve_positive_value`(§9.2). 다중 예측 파생은 같은 규칙으로 만든 표기 → 원래 값 표를 쓴다. 표기를 만들어
  내보내는 쪽(metadata 의 이진 클래스 판단·알려진 정답 목록·확률 컬럼 클래스 확정)은 `normalize_label` 을 쓴다.
- **검증의 클래스 불일치 검사는 평가와 같은 표기로 비교한다**: `validation_checks.check_class_mismatch` 는
  `normalize_label`(정수 값 float → 정수 표기, 앞뒤 공백도 지움)로 비교한다 — 평가 전처리와 같은 표기라 정답 1.0 과
  예측 1, 정답 `' cat'` 과 예측 `'cat'` 은 같은 클래스다. 표기가 실제로 바뀐 값은 `check_label_notation` 이 따로
  알린다(평가 경고와 같은 `label_notation_changes`). `normalize_label` 은 `label_text` 에 공백 제거를 더한 것이라 숫자
  표기 규칙은 한 곳에 있다.
- **평가 프레임의 라벨 값**(`preprocessor._normalize_hard_labels`): 정답·예측 하드 라벨을 한 표기로 맞춘 뒤 지표를 낸다.
  둘 다 빈 값 없는 정수 값 숫자(int, 1.0 같은 정수 float)면 **int64** 로 두고, 그 밖은 `normalize_label` 문자열로 바꾼다
  (`unify_hard_label_columns`). 숫자 라벨까지 문자열로 바꾸면 sklearn 이 지표마다 문자열 배열을 정렬해 80만 행(10MB)
  평가가 2초대에서 40초 넘게 걸렸다. 응답의 클래스 이름(M21 `labels`·M22 키·분포 키)은 어느 쪽이든 표준 이름 문자열이고,
  sklearn 에 넘기는 `labels` 는 `metrics.common.class_values` 로 이름 → 데이터 값을 찾아 쓴다.
- **불리언 라벨**(`preprocessor.align_boolean_labels`, 평가 전처리·검증이 같이 씀): `proba > 0.5` 를 그대로 저장한 True/False
  예측과 0/1 정답처럼 한쪽만 불리언이면 **예측이 정답 표기를 따른다** — 정답이 숫자(또는 표기가 0/1 뿐)면 예측을 1/0 으로,
  정답이 불리언이고 예측 표기가 0/1 뿐이면 예측을 True/False 로. 둘 다 불리언이면 `'True'`/`'False'` 그대로다.
  불리언인지는 dtype 이 아니라 값으로 본다 — 빈 칸이 섞여 object 로 읽힌 True/False 컬럼도 불리언이다.

## 10. 서술(7·8·9절) — 작업 번호 · 장별 생성 · 칸별 검문 사다리 · 규칙 템플릿 (2026-10, AI 서술 설계 구현 라운드)

한 줄 요약: **서술은 소절 7칸 단위로 만들고, 검사하고, 바꾸고, 기록한다.** 숫자·판정은 코드가 정하고, AI 는 코드가 뽑은
결론을 문장으로 옮긴다. AI 가 실패하거나 검사에 걸린 칸만 규칙 문장으로 바꾼다.

### 10.1 두 경로

| 경로 | 누가 쓰나 | 방식 |
|---|---|---|
| `POST /api/narrative/jobs` → `GET /api/narrative/jobs/{id}` (새) | 운영 프론트(2026-10-23 배포부터) | 작업 번호와 8.1 벤치마크 표를 **바로** 주고, 서술은 BackgroundTasks 의 `jobs.run_job` → `generator.generate_sections` 가 만든다. 품질 우선(effort `high`, 최대 10분) |
| `POST /api/generate-narrative` (옛) | 옛 클라이언트(운영 프론트는 더 이상 부르지 않음) | 한 번 호출로 일곱 칸을 받는다(`legacy.py` 에 그대로 얼림, effort `low`, 서버 마감 120초 — 넘으면 200 + 규칙 문장). 다음 라운드에 지운다 |

두 경로는 같은 사실 시트(`FactSheet`)·같은 숫자 허용 목록·같은 규칙 템플릿을 쓴다. 판정(verdict)은 늘 사실 시트 값이다(AI 가 정하지 않는다).
이 절의 칸 이름(7.1~9)은 판 3 성적서의 번호다. 판 4 성적서용 요청(`report_edition: 4`)은 같은 일곱 칸을 판 4 자리(5.x·6.x)로 옮겨 쓴다 — §13. 옛 경로는 늘 판 3 이다.

### 10.2 소절 7칸 (`sections.py`)

7.1 혼동행렬 해석 · 7.2 분포·불균형 · 7.3 추가 관찰 · 8.1 벤치마크 · 8.2 종합 총평 · 8.3 리스크 · 9 권고(9.1·9.2 서술 + 권고표가 한 칸).
7.3 은 결론 목록 밖에서 AI 가 찾은 것만 쓰는 칸이라 규칙 문장이 없다 — AI 가 쓰지 않았거나 검사에 걸리면 비우고 성적서가 "해당 없음"(고정 문구 15)을 찍는다.

### 10.3 필수 서술 항목과 결론 목록 (`required_items.py`)

성적서 절마다 반드시 다룰 항목 42개를 표로 둔다(항목 ID `7.1-01` … `9-03`). `select_items(사실 시트, 고객 입력, 작업 유형)` 이
이 성적서에 해당하는 항목만 남기고 숫자를 채운 **결론**을 만든다. **AI 지시문과 규칙 템플릿이 같은 목록을 읽는다** — 그래서
AI 가 쓸 내용과 규칙 문장이 쓸 내용이 어긋나지 않는다.

| 작성 주체 | AI 지시문 | 규칙 템플릿(`Conclusion.template_text`) |
|---|---|---|
| ai | '반드시 다룰 결론' | 결론 문장 그대로(서술체). 판정 사유·불균형·임계값 위험처럼 규칙 문장이 따로 있는 항목은 그 문장 |
| ai_fact (모델 용도·평가 데이터의 대표성과 한계·최약 클래스의 용도상 위험) | AI 가 해석 | **사실 문장만**("의뢰자가 밝힌 모델 용도는 '…'이다.", "의뢰자가 밝힌 평가 데이터 출처는 '…'이다.") — 해석은 지어내지 않는다 |
| fixed_interpret (오분류의 성격·근소 차이 지표) | '해석만 쓸 결론' + 해석 재료(우세한 오류, 근소 지표가 충족했는지) | 성적서가 고정 문구 17·18 로 숫자를 찍으면 **숫자 없는 해석 한 문장**, 찍지 않는 옛 요청이면 숫자 문장 |
| fixed · form | '성적서가 따로 찍는 문장'(되풀이 금지) | 쓰지 않는다 |

- 고정 문구 16(8.1 표 아래, 프론트가 계산해 `facts.fixed_sentences` 에 `id "16"` 으로 보냄): 서술 지표 가운데 기준표에 없는 지표가
  **일부**면 "다음 지표는 내부 참조 기준치가 없어 벤치마크 비교를 하지 않았다: {지표}." — 지시문의 '성적서가 따로 찍는 문장'에 이 원문이
  실린다. **전부**면 "선택한 지표에 내부 참조 기준치가 없어 벤치마크 비교를 하지 않았다." — 8.1 칸은 출처 `fixed`·빈 글(아래 10.4).
  `facts` 가 없는 옛 요청과 옛 경로는 종전 문장("비교 가능한 내부 참조 기준치가 없어 벤치마크 비교를 생략한다.") 그대로.
  프론트는 판 3 성적서에서 8.1 이 출처 `fixed`·빈 글이면 자리표시자를 찍지 않고 표·고정 문구 16 만 그린다(계약 — 빈 8.1 을
  다른 출처로 보내면 화면이 "서술 없음" 자리표시자를 찍는다).
- 고객 입력 값이 비었거나 "제공되지 않음"으로 **시작**하면 제공되지 않은 것이다(`wording.is_not_provided` 한 곳). 프론트는 "모름" 선택을
  "제공되지 않음"으로, "모름 + 덧붙이는 글"을 "제공되지 않음 (의뢰자 제공: …)" 로 보낸다 — 괄호 안 글은 참고 글일 뿐이라 결론(예: 8.2-12
  지표 선택 기준)을 살리지 않고, 지시문 규칙 17(판 4 는 19)이 AI 에게 "의뢰자가 정했다·골랐다"고 쓰지 말라고 한다. 글 칸에 의뢰자가
  "모름"이라고 직접 적은 글은 제공으로 센다 — 프론트 재료 점검(줄 값이 있으면 제공)과 판정이 갈리지 않게.
- 8.2 평균 방식 차이(8.2-07 다중 매크로 vs 가중, 8.2-08 멀티레이블 매크로 vs 마이크로, D17·D39)는 지표 선택(M22)과 무관하게 쓴다 —
  클래스별 표는 엔진이 늘 계산하고(`class_report`), 프론트가 그 평균 행으로 `facts.average_gap` 을 늘 싣는다. 값이 없으면(정답 클래스 둘
  미만, 옛 요청) 쓰지 않는다. (2026-10, 심판 라운드 1단계. 그 전에는 M22 를 골랐을 때만 썼다.) 높다·낮다·같다 갈래는 **찍히는 차이**
  (`difference_text`)로 고른다 — 그 글자가 0("0"·"0.000")이면 "두 값이 같다"(반올림 전 값으로 고르면 "보다 0 낮다"가 찍혔다).
- 8.2 평가 데이터의 대표성과 한계(8.2-14, ai_fact, 판 3·4 모두): TS 4213 보고 항목 2 "평가 데이터 출처"가 제공되면 나온다 — 고객 입력
  `test_data` 의 "평가 데이터 출처"와 "학습 데이터와의 관계" **두 줄 모두** 제공(재료 선택 점검의 셈: 한 항목의 모든 줄이 있어야 제공).
  하나라도 빠지면 성적서 1.3(판 3 은 1.4)이 "평가 데이터 출처: 평가 데이터가 용도를 대표하는지 판단할 수 없다."를 찍으므로 8.2(판 4 는
  5.1)에서 대표성을 해석하지 않는다(프론트 재료 점검 항목 2 와 같은 판정 — 백엔드에서는 `required_items._eval_data_source` 한 곳).
  두 저장소가 같은 판정인지는 같은 바이트로 두는 대조 표 `tests/contract/reporting_item2_cases.json` 이 지킨다 — 프론트 시험은 같은
  입력에서 앱이 보내는 `test_data` 와 재료 점검 판정을, `tests/test_j1_item2_contract.py` 는 그 `test_data` 로 8.2-14 가 나오는지를
  본다. 셈을 바꾸면 두 저장소의 코드·표·sha256 을 함께 고친다. 알려진 경계 하나(표의 `pending`): 의뢰자가 출처 글 칸에 "제공되지
  않음"(으로 시작하는 글)을 직접 적으면 프론트는 제공, 백엔드는 빈 칸 대신 오는 말과 글자가 같아 제공 아님으로 센다(글로 적은 "모름"의
  셈과 함께 정할 일). 관계만 있고 출처 글이 없어도 나오지 않는다. AI 에게는 출처를 인용해 평가 데이터가 모델
  용도(용도가 없으면 실제로 쓰일 환경)를 얼마나 대표하는지와 그 한계를 해석하되, 의뢰자 입력만으로는 대표성을 확인할 수 없으니
  "대표한다·대표하지 못한다"고 단정하지 말고 "~로 보인다"처럼 추론으로 쓰라고 한다 — 고객 정보만으로 품질을 단정하는 문장("평가 데이터는
  용도를 잘 대표한다")은 서술 심판 설계가 위반으로 본다. 규칙 템플릿은 출처 사실 한 문장만 찍는다. 평가 데이터 수집 기간은 이 항목의 조건·
  문장에 넣지 않는다(다른 고객 입력처럼 AI 에 그대로 간다 — D25).
- "성적서가 17·18·16 을 찍는가"는 `required_items.code_prints` 한 곳에서 정한다. 새 프론트(사실 시트에 `facts` 가 있음)는 찍는다 —
  `facts` 가 상한을 넘어 고정 문장 목록을 비웠어도(`omitted.fixed_sentences`) 화면은 찍는다. 옛 프론트(`facts` 없음)는 찍지 않는다.
- 작성 규칙(아래 D37): 클래스는 `이름(설명)`(고객 입력 `class_label_descriptions`), 영어 코드값·필드명을 쓰지 않음, 서술체 완결
  문장(개조식·`항목: 값` 꼴 없음). 조사(은/는·으로/로)와 숫자 표기는 `wording.py` 한 곳. AI 지시문 규칙 8 은 영문·숫자 이름 뒤 조사를
  영어 발음의 끝소리로 고르게 한다(benign과, cat과, dog와, P3이 — 세션 C 실호출에서 'benign와'·'P3가'가 나왔다).
  조사 규칙은 프론트 `koreanJosa.josaWaGwa`(3절)와 같은 공통 규칙이다(세션 C 마지막 검토 — 같은 이름에 3절과 7.2 가 다른 조사를 찍었다):
  끝 따옴표·공백은 건너뛰고, '이름(설명)'은 괄호 앞 이름으로(2(정상)와), 숫자는 읽는 소리(소수는 끝 숫자, 정수는 십·백·천·만…),
  영문 대문자 끝은 알파벳 이름(L·M·N·R 만 받침), 소문자 끝은 -ng·-m·-n·-l·-ck 와 모음 뒤 -t 만 받침(cat과·malignant와·test와),
  정할 수 없으면 '와(과)'·'은(는)'. 같은 대조 표를 두 저장소 테스트(`tests/test_session_c_final_review.py`)에 박았다.
- 숫자 표기: 판정과 비교되는 값은 프론트가 판정과 같은 쪽으로 읽히게 만든 표시 문자열(`value_text`·`margin_text`·`*_text`)을 그대로,
  지표 값·목표값·구간 끝은 성적서와 같은 셋째 자리(목표와 같아 보이면 자릿수를 늘림), 그 밖의 실수는 넷째 자리.
  8.1 참조 범위 비교의 모델 값(규칙 문장·사실 시트 보기)은 그 표기가 범위 끝과 같아 위치 판정(반올림 전 값)과 반대로 읽히면 자릿수를
  늘린다(`required_items.benchmark_value_text` → `wording.range_value_text` — 0.79996 은 '0.8' 이 아니라 '0.79996, 참조 범위 0.8~0.92').
  규칙은 프론트 8.1 표(`judgedNumber.formatBenchmarkValue`)와 같다(세션 C 마지막 검토 — 최대 자릿수가 9·6 으로 달라 표와 서술 숫자가
  갈렸다): 최대 **여섯째 자리**, 그래도 반대로 읽히면 위치 쪽으로 자른다(아래는 내림·위는 올림). 판정 대상 지표면 같은 표기가 목표
  판정(충족/미달)과도 맞아야 하고, 둘 다 맞는 표기가 없으면 목표 판정이 우선(6.1 표기). 같은 대조 표를 두 저장소 테스트에 박았다.
  늘린 표기는 숫자 허용 목록에도 들어간다(`grounding.build_number_whitelist` 가 같은 함수를 부른다).
  응답의 벤치마크 표(`model_value`)는 계약대로 넷째 자리 숫자 그대로다.
- 오류 성격 해석 재료(7.1-11, 세션 C): 우세한 오류에 더해 근거 건수(확률이 있는 오분류·경계·확신·둘 다 아닌 오류 — 둘 다 아닌 건수는 두 오류가
  겹칠 수 없을 때만, `required_items.error_breakdown`)를 싣고 "문장에 쓰지 않는다"고 적는다. 오분류가 `ERROR_NATURE_MIN_COUNT`(10)건 미만이거나
  경계+확신 오류가 오분류의 과반이 아니면(두 오류가 겹칠 수 있으면 많은 쪽 하나로 본다) '상당 부분·대부분·우세한 성격' 같은 일반화를 막고
  "경계 오류가 확신 오류보다 많다" 수준만 쓰게 한다. '오류의 주된 성격으로 해석해도 된다'는 우세한 쪽 **하나**가 과반일 때만 싣고, 두 오류의
  합만 과반이면 "경계 오류와 확신 오류를 합치면 오분류의 절반을 넘는다"고만 쓰게 한다(세션 C 마지막 검토 — 20건 중 경계 6·확신 5 에
  '경계 오류가 절반을 넘는다'고 썼다).
  확신 오류가 오분류의 소수면 '확률이 높은 예측 전반을 믿을 수 없다'는 일반화를 막는다. 둘 다 아닌 건수는 생성기가 허용 목록에 넣는다.
- 근소 차이 지표(8.3-02, 세션 C): 해석 재료에 지표마다 신뢰구간이 목표값을 포함하는지(`ci_contains_target`)를 싣는다. 포함하지 않는 지표는
  AI·규칙 문장 모두 "표본이 달라지면 판정이 뒤집힐 수 있다"를 쓰지 않고 목표와의 여유가 작다는 사실만 쓴다(8.2 의 '구간이 목표와 떨어져
  있다'와 부딪치지 않게). 8.3 지시문은 여유·아슬아슬 해석을 사실 시트의 근소 차이 지표에만 쓰게 한다.
- 임계값 조정 여지(D40)는 F1 만 본 판단이다(세션 C): 사실 시트 보기에 '판단 기준'을 싣고, 7.3·8.2·8.3·9 지시문이 Recall 등 다른 지표 문제에
  '임계값 조정이 소용없다'고 적용하지 못하게 한다. 엔진이 조정 여지가 작다고 봤으면 8.3 에 임계값을 위험으로 쓰지 않게 한다.
- 최약 클래스 동점(세션 C, `required_items.weakest_ties`): 클래스별 표에서 F1 이 최약 클래스와 같은(인쇄 자릿수 넷째 자리 기준) 클래스가 더 있으면
  7.1-10·8.3-01 결론과 규칙 문장이 "F1 0으로 같은 두 클래스(2, 8)"처럼 함께 부르고(개수는 우리말 — 열 넘으면 '여러', 이름은 다섯까지),
  7.1·8.3 지시문이 하나만 단독 최약처럼 쓰지 못하게 한다. 표가 잘렸으면 '표에 실린 클래스 가운데'로 한정한다.
- 지표의 평균 방식(세션 C, `fact_view.averaging_text`): 사실 시트 보기의 지표 줄에 '평균 방식'을 싣는다 — 엔진에서 Precision·Recall·F1·F-beta 는
  이진이면 양성 클래스 기준, 다중·멀티레이블이면 매크로 평균, 멀티레이블 Jaccard 는 표본 평균. 다중·멀티레이블의 7.1·8.2·8.3 지시문은 매크로
  평균에 '평균에는 약한 클래스 부진이 드러나지 않는다'(가중·마이크로에만 맞는 말)를 쓰지 못하게 한다.
- 7.2 불균형 말투는 성적서 3절 불균형 진단과 같다(사용자 결정 2026-10-22): 엔진 판단이 '영향 있음'(affected)이면 결론·규칙 문장·지시문 모두
  "불균형에 따른 성능 지표 왜곡이 관찰되었다"로 쓰고, '불균형이 성능 수치에 영향을 주었다·준 것으로 보인다' 같은 인과 단정은 쓰지 않는다.
  소수 클래스의 크기는 세 상태다(`required_items.minority_size`): 작음(`facts.low_support_classes` 에 있음)이면 "표본이 적어 수치가
  흔들리기 쉬우니 해석에 유의", 작지 않음(목록이 온전한데 없음)이면 지시문이 '표본이 적은 클래스가 아니므로'를 싣고, 모름(facts 없음,
  `facts.omitted` 의 `low_support_classes`·`facts_class_lists`, 목록을 보내지 않음)이면 표본 크기를 단정하지 않고 '소수 쪽 해석에 유의'만
  싣는다. 규칙 문장은 작음일 때만 '표본이 적어', 그 밖은 "소수 클래스의 성능 지표 해석에 유의"(세션 C 재확인 실호출에서 64건 클래스에
  '표본이 적어'가 붙었다; 마지막 검토 — 모름을 작지 않음으로 단정했다). 덜 중요하게 보라는 뜻으로 읽히는 말('같은 무게로 읽지 않도록')을
  지시문이 막고, 의뢰자가 '모든 클래스가 동등'을 밝혔으면 그 선언도 지시문에 싣는다.
- 판정 문장 규칙(지시문 규칙 7): 미달한 지표가 있으면 그 미달이 종합 판정과 무관하다·영향이 없다고 쓰지 않는다(비핵심 미달은 조건부
  합격의 사유). 오류 성격 재료는 건수가 충분하고 우세한 쪽 하나가 과반이면 '주된 성격으로 해석해도 된다'를 함께 싣는다(합만 과반이면 합이 절반을 넘는다고만).
- 엔진 `success_metrics.imbalance_effect`(불균형 영향, D20)는 판정 세 값(`imbalance_ratio`·`accuracy_minus_macro_f1`·
  `majority_minus_minority_f1`, 표시는 판정 쪽으로 자릿수를 늘린 `judged_text`)과 함께 차이를 만든 네 값 `accuracy`·`macro_f1`
  (판정과 같은 정의 — 클래스별 F1 단순 평균; 멀티레이블은 둘 다 null)·`majority_f1`·`minority_f1` 를 싣는다. 네 값의 `display` 는 판정과
  무관해 엔진 평소 넷째 자리(`display.plain_text`). 성적서 3절 불균형 진단 문장의 재료이고, 사실 시트에 실리면 숫자 허용 목록에도 든다.

### 10.4 생성 흐름 (`generator.py`)

1. 장마다 한 번 — 7장(7.1·7.2·7.3)·8장(8.1·8.2·8.3)·9장(9)을 **동시에** 부른다. 문제 목록이 0개면 9장은 부르지 않는다(9칸은 규칙 문장, 출처 fixed).
   서술 지표 전부가 기준표에 없고 성적서가 고정 문구 16 을 찍으면(`required_items.benchmark_printed_only` — 참조 표가 비고, 비교 기준 없음
   항목 `8.1-03` 이 있고, `code_prints(…, "16")`) 8장 호출에서 8.1 만 뺀다(8.1 = 빈 글, 출처 fixed — 8.2·8.3 은 늘 있어 8장 호출은 남는다).
   8.1 을 부르지 않으니 빈 칸 검사는 그대로다(AI 가 쓴 빈 8.1 은 여전히 위반).
2. 모든 호출은 같은 사실 시트(AI 가 읽는 한국어 보기 — `fact_view.py`)와 결론 목록 전체를 받고 자기 장의 칸만 쓴다.
   다른 장 옆에 성적서가 숫자로 찍는 문장(17·18)은 "되풀이하지 않는다"로 알린다.
3. 호출 실패: 429(사용 한도)는 차례로 한 번 더, 호출 오류·시간 초과·JSON 오류는 한 번 더. 거절(refusal)·잘림(max_tokens)·모델 없음은
   **같은 요청으로 다시 부르지 않고** 그 장의 칸을 규칙 문장으로 — 거절된 요청은 약 1시간 동안 대체 모델로 고정 라우팅되기 때문이다.
4. 호출은 `llm.py` 한 곳: `client.beta.messages.create(model=claude-sonnet-5-5, betas=["server-side-fallback-2026-07-01"],
   fallbacks="default", max_tokens=16000, output_config={format: json_schema, effort})`, 비스트리밍, 온도·seed 없음.
   응답 스키마와 지시문에 추론 과정·근거 필드를 두지 않는다(그런 거절은 대체 모델이 없다).

### 10.5 칸별 검사와 검문 사다리 (`checks.py` · `grounding.py`)

| 검사 | 무엇을 | 걸리면 |
|---|---|---|
| ① 숫자 | 그 칸 글의 숫자가 모두 허용 목록 안(원본 사실 시트·파생값·고객 입력에서 만든 목록) | 그 칸만 1회 다시 → 또 걸리면 그 칸만 규칙 문장 |
| ② 판정 모순 | 판정과 어긋나는 단정(불합격인데 "모두 충족" 등 — 부정·조건·규칙 설명은 뺌) | 같음 |
| ③ 9칸 | 기대 효과의 예측 수치(지표값·향상폭 — '1차 원인'·'3개월 내'는 막지 않음. 숫자 꼴 클래스 이름 '클래스 2'·'2(…)'도 뒤에 건·개·칸·%·배나 개선 낱말이 붙지 않으면 막지 않음 — `checks.numeric_labels`), 권고가 빠진 문제 | 같음. 권고 하나만 빠졌으면 다시 만들고, 또 빠지면 그 문제만 종류별 권고 템플릿으로 채움 |
| ④ 선언 숫자(D24) | 의뢰자 선언이 있으면 그 숫자가 글에 있는가(7.1 위험 쪽 오류·8.2 선언 평균 방식·8.3 대화형 응답 시간) | 1회 다시 만들고, 그래도 없으면 **그대로 싣고 기록** |
| ⑤ 형식 | 빈 칸, 7.3 의 숫자 인용, 영어 판정 코드·밑줄 필드명 | ①과 같음(7.3 은 다시 만들지 않고 비움) |

- 한 칸의 HTTP 호출은 최대 2회(첫 장 호출이 재시도됐으면 그 칸은 다시 만들지 않는다). 숫자와 선언이 함께 걸려도 다시 만들기는 1회.
- 다시 만들기는 그 칸만 요청하는 호출이다(같은 사실·결론, 위반 숫자는 넣지 않음).
- 칸을 섞은 최종본에 판정 모순 검사를 한 번 더 한다(조립 결함 방어).
- 판정 모순 검사 전에 판정 낱말(미달·불합격 등)이 든 클래스 이름·고객 클래스 설명을 가린다(`checks.verdict_masks`) —
  '1(불합격품)' 을 부른 맞는 문장이 '미달했다'는 주장으로 읽히지 않게. facts 목록에만 남은 클래스 이름(잘린 표 밖)도 이름으로 본다.
- 시간: 작업 전체 10분 안에서 호출마다 남은 시간으로 제한을 줄인다. 남은 시간이 30초보다 적으면 부르지 않고 그 칸을 규칙 문장(사유 deadline).

### 10.6 규칙 템플릿 (`fallback.py`)

칸 함수 7개(`SECTION_TEMPLATES`)가 결론 목록의 템플릿 문장을 표 순서대로 잇는다. 결론 목록 밖의 문장은 칸의 앞뒤 사실 문장뿐이다
(7.1 혼동행렬이 없다는 말, 7.2 분포 나열, 8.1 기준의 출처, 8.3 목표 미달 위험, 9절 9.1·9.2 문장과 권고표). 옛 경로·키 없음은
일곱 칸을 모은 `build_fallback_narrative`, 작업 경로 사다리는 걸린 칸만 `section_template` 을 부른다.

- 작업 유형·고객 입력은 두 경로가 넘긴다. 넘기지 않은 옛 호출은 사실 시트로 짐작한다(`required_items.infer_task_type`).
- 클래스가 많아 프론트가 표를 잘랐으면(`facts.omitted`) 잘린 표에서 '가장 많은'·'전부'를 단정하지 않는다(실린 클래스 가운데로 한정).
- `facts` 가 없는 옛 요청(옛 프론트, 저장된 다시 만들기 요청)에서도 깨지지 않는다. 혼동행렬(M21)을 고르지 않아 행렬이 없으면
  엔진 클래스별 건수(`confusion_counts`)로 오분류 총건수를 센다(옛 요청만의 서버 셈 — 새 요청은 `facts.error_totals` 를 옮긴다).
- 검증(`tests/test_s6_templates.py`): 작업 유형 3 × 판정 4 가지로 템플릿 출력이 자기 검문(①②④⑤)을 통과, 17·18 숫자 묶음이 다시
  나오지 않음, 옛 경로 골든(`narrative_legacy_main_fallback` — 옛 경로 모양)과 새 골든(`narrative_job_fallback_*`)을 따로 둔다.

### 10.7 기록 둘과 작업 표 (`jobs.py` · `models.py`)

- **고객용**(조회 응답 `result`): 서술 본문 + 칸별 출처(`section_sources` — `llm` · `fallback`(규칙 문장으로 대체) · `fixed`(고정 문구))
  + 칸별 모델 이름(`section_models` — 키는 일곱 칸 전부, `llm` 칸만 그 글을 낸 호출의 응답 모델이고 `fallback`·`fixed` 는 null. 다시 만든
  글이면 다시 만든 호출, 첫 글을 둬 뒀다 실으면 첫 호출의 모델. 작업 행 상한으로 바로 규칙 문장인 경우도 전부 null). 성적서 화면의 '작성
  기록'에 쓰인다(사용자 결정 2026-10-22 — 그 전에는 모델을 내부용에만 뒀다). 번호만 알면 열리므로 이것만 싣는다.
- **내부용**(`internal_json`, 서버 로그): 실패 종류, 칸마다 출처·결과(first·second·kept_first·filled·template·dropped·fixed)·시도 수·
  검사 기록, 호출마다 목적·칸·응답 모델(대체 모델 포함)·대체 요청을 보냈는지·거절 종류·토큰·비용·슬롯 대기, 429 횟수, 단계별 시각,
  7.3 원문. 입력(사실 시트·고객 입력)은 저장하지 않는다 — 작업은 메모리의 요청으로 돌고, 서버가 재시작되면 유실이 된다.
- 표 `narrative_jobs`: `status`(running·done·failed) · `stage`(queued·generating·checking·regenerating·judging(판 4 만, §14)·done·failed) · `result_json` ·
  `internal_json` · `created_at`/`updated_at`/`finished_at`(tz 없는 UTC). **열은 확정** — 앞으로는 두 JSON 칸 안에서만 늘린다(§7 규칙 4).
- 끝나는 방식: 서술이 생기면 AI 든 규칙 문장이든 **완료**(키 없음·지갑 소진·호출 실패·검사 위반·입력 상한 초과 모두). **실패**는 전체 10분
  초과(timeout)·멈춤(lost — 마지막 갱신 뒤 360초 또는 만든 뒤 630초, 조회 때 판정)·예기치 않은 오류(error)·결과 글을 지움(expired).
- 장별 호출이 동시에 단계를 쓰므로 단계 쓰기는 하나씩(`asyncio.Lock` — SQLite 는 연결 하나를 스레드끼리 같이 쓰면 깨진다).
- **Postgres 왕복**(로컬): `docker run -d --name <이름> -e POSTGRES_PASSWORD=<비번> -p 127.0.0.1:55433:5432 postgres:17-alpine` 뒤
  `NARRATIVE_PG_URL=postgresql://postgres:<비번>@127.0.0.1:55433/postgres venv/bin/python -m pytest tests/test_postgres_roundtrip.py`.
  작업 생성 → 장 셋 동시 단계 쓰기 → 완료 → 조회, 라우트 왕복, 유실·만료 판정을 본다. CI 에서는 건너뛴다.

### 10.10 왜 이렇게 만들었나 — 처음 설계 때 정한 것 중 지금도 그대로인 것

- **AI 는 숫자를 만드는 쪽이 아니라 옮기는 쪽이다.** 모든 숫자는 평가 엔진(`app/evaluation/`)과 서버 파생 계산이 정하고,
  AI 는 그 값을 한국어 문장으로 옮기기만 한다. 그래서 숫자 검문(§10.5 ①)이 "허용 목록 밖 숫자 = 지어낸 숫자"로 볼 수 있다.
- **평가(`/api/evaluate`)와 서술(`/api/narrative/jobs`)은 따로 부른다.** 서술 AI 가 실패해도 지표 계산이 500 이 되지 않고,
  지표·차트는 바로 보이며 서술만 뒤에 온다. 다시 만들 때도 원본 CSV 를 다시 올리지 않고 사실 시트(수 KB)만 보낸다.
- **판정(verdict)은 프론트 `src/lib/report/computeVerdict.ts` 가 규칙으로 계산한다**(AI 가 정하지 않는다). 백엔드는 사실 시트에
  실려 온 판정을 그대로 쓴다. 판정 대상은 **목표값이 있고 산출에 성공한 지표만**이다(혼동행렬 같은 정보 제공 지표는 빠진다).
  핵심 지표(미달이면 불합격)의 기본값은 유형별로 이진·다중 클래스 = Accuracy(M1)·F1(M4, 다중은 매크로),
  멀티레이블 = F1(M4)·Jaccard(M17)이고, 사용자가 합격 기준 화면에서 바꿀 수 있다. 판정 규칙 네 단계는 §10.9 D19.
- **8.1 벤치마크는 고정된 참조 표(`app/narrative/baselines.py`)로 비교한다 — 웹·벡터 DB 검색(동적 RAG)은 쓰지 않는다.**
  검색 결과는 실행마다 달라져 같은 성적서를 다시 만들 수 없고, 출처를 확인할 수 없는 숫자가 성적서에 들어갈 수 있기 때문이다.
  표의 범위는 공개 벤치마크 평균이 아니라 내부에서 정한 보수적인 기준이라 **"내부 참조 기준치"** 라고 부르고, 출처 문구
  (`SOURCE_NOTE`)를 함께 싣는다 — 권위 있는 외부 기준처럼 보이지 않게. 모델 값이 범위의 아래·안·위 어디인지는 서버가 계산하고
  (AI 는 위치를 문장으로 옮길 뿐), 표에 없는 지표는 비교하지 않는다(고정 문구 16). 나중에 실제 도메인 기준으로 바꾸려면
  `get_baseline()` 한 곳만 바꾸면 된다.

## 11. 발급(issuance) — 성적서 번호·정정 발급·보관본

한 줄 요약: **번호는 '발급' 버튼을 누를 때 받는다. 같은 평가(run)는 몇 번 눌러도 번호가 하나이고, 고칠 때는 번호를 그대로 두고 차수만 올린다.**

- **번호 규칙**: `RPT-{연도}-{순번 4자리}`(예: `RPT-2026-0001`). 순번은 해마다 1 부터 다시 센다. 연도는 한국 시간(KST) 기준이다 —
  UTC 연도를 쓰면 1월 1일 오전(KST)에 발급한 문서가 번호는 전년도, 발급일은 새해가 된다.
- **번호를 받는 때**: 평가가 끝났을 때가 아니라 사용자가 **발급**할 때다. 평가만 하고 버린 run 에 번호를 낭비하지 않고, 번호가 있으면
  발급본, 없으면 초안이라는 뜻이 분명해진다.
- **같은 run = 같은 발급(멱등)**: `POST /api/reports/issue` 를 같은 `run_id` 로 다시 부르면 새 번호 없이 기존 발급본을 돌려준다.
  `report.run_id` 에 UNIQUE 제약이 있어 동시에 두 번 눌러도 번호가 둘 생기지 않는다.
- **정정 발급**: `POST /api/reports/{no}/reissue` 는 번호를 그대로 두고 차수를 올린다(`v1.0` → `v1.1` → `v1.2`). 이전 차수 행은
  `superseded`(대체됨)로 바뀌고 새 차수가 `issued` 다. 요청에는 `run_id` 가 꼭 있어야 하고, 그 성적서의 run 과 다르면 거절한다(번호는
  차례로 셀 수 있지만 run_id 는 추측할 수 없어서, 번호만 아는 제3자가 남의 성적서를 정정하지 못한다).
- **동시에 발급할 때**: `UNIQUE(year, seq)` 와 `UNIQUE(report_id, version)` 제약이 같은 번호·같은 차수가 두 번 저장되는 것을 막고,
  부딪히면 되돌린 뒤 다시 계산해 **최대 5번** 다시 시도한다(`service.py` `_MAX_NUMBERING_RETRIES`). SQLite 에서는 트랜잭션을
  `BEGIN IMMEDIATE` 로 열어 쓰기를 한 줄로 세운다(PostgreSQL 에는 적용되지 않음 — 제약 + 재시도가 방어선, §8.2 F-12).
- **기관(organization)은 한 행뿐**(id=1). 기동 때 표가 비어 있으면 기본 기관("리트머스")을 넣는다(`bootstrap.py`). 기관을 바꾸는
  API(`PUT /api/organization`)는 **일부러 두지 않는다** — 인증이 없는 상태에서 누구나 이미 발급한 성적서의 기관 표기를 바꿀 수
  있었기 때문이다. 바꿀 때는 §12 처럼 DB 에서 한 번 직접 바꾼다.
- **발급 시점 보관본**: 차수마다 `report_snapshot` 한 행에 그때의 기관 정보(`org_snapshot_json`)와, 프론트가 보낸 성적서 원본
  (`content_json`, 선택, 1 MiB 상한)과 그 SHA-256 을 저장한다. 그래서 나중에 기관 이름을 바꿔도 이미 발급한 성적서의 표기는
  그대로다. 보관본이 없는 옛 발급본은 현재 기관 행으로 보여 준다(없던 사실을 소급해 만들어 넣지 않는다).
  원본은 `GET /api/reports/{no}/content`(`?version=v1.0` 으로 이전 차수)로 다시 받는다. 발급 이력에는 직전 차수와 비교해 값이
  바뀐 최상위 절 목록이 붙는다.
- **시각**: DB 에는 tz 없는 UTC 로 저장하고, 응답의 `issued_at` 은 `+00:00` 오프셋을 붙인 ISO8601 로 내보낸다. 오프셋이 없으면
  프론트가 한국 시간으로 잘못 읽어 날짜가 하루 어긋날 수 있다. 화면 표기(KST)는 프론트가 한다.
- **판 4 성적서**: 첫 발급과 정정 발급 모두 요청의 `narrative_job_id` 가 "판 4 · 완료 · 심판 통과" 작업이어야 하고, `content` 의 서술 글이 그 작업이
  통과한 글과 같아야 한다. 아니면 409 와 사유 코드(§14.6). 판 1~3 성적서는 이 검사를 받지 않는다.
- **가짜 데이터 0**: 발급 전 성적서는 가짜 번호를 만들지 않고 "초안(미발급)"으로 표시한다(프론트). 서버도 모르는 값은 지어내지 않는다.
- **표**: `organization`(기관 1행) 1 : N `report`(번호 단위) 1 : N `issuance`(차수 이력), `report` 1 : N `report_snapshot`(차수별 보관본).
  서술 작업 표 `narrative_jobs` 는 발급과 관계없는 따로 선 표다(§10.7). 다섯 표 모두 기동 때 `init_db()` 의 `create_all` 이 만든다.

## 12. 배포·운영

한 줄 요약: **팀 저장소 main 에 push → CI 통과 → 포크로 복사 → Render 가 빌드. 되돌릴 때는 Render 의 Rollback 이 아니라 되돌리는 커밋으로.**

| 구분 | 실제 값 |
|---|---|
| 백엔드 | Render 무료 web service — `https://capstone-back-59z8.onrender.com` |
| 프론트 | Vercel — `https://capstone-beta-lilac.vercel.app`. 빌드 때 `VITE_API_BASE_URL` 로 Render 주소를 넣고, 브라우저가 백엔드를 **직접** 부른다(Vercel 프록시는 응답을 약 30초에 끊어 콜드 스타트·긴 LLM 응답에서 실패한다) |
| DB | Neon PostgreSQL(무료, 연결 문자열은 Direct connection). Render 무료 Postgres 는 30일 뒤 만료되고, Supabase 무료는 7일 쉬면 일시 정지돼 손으로 살려야 해서 Neon 을 골랐다 |

**배포 경로**

1. 팀 저장소(`hwanginyong02/Capstone_Back`) `main` 에 push.
2. CI(`.github/workflows/ci.yml`)의 test job — `pytest -q` 뒤 실제로 서버를 띄워 스모크: `/health` → `/api/organization` →
   발급 → 발급정보 조회 → `/content` 원본 조회 왕복 → 서술 작업 `POST /api/narrative/jobs` → `GET` 이 `done` 이 될 때까지 보고,
   칸 출처가 `fallback`·`fixed` 뿐인지(키 없는 CI 라 AI 칸이 없어야 함) 확인.
3. deploy job — 포크 `hellinii/Capstone_Back` 의 `main` 으로 그대로 복사(force push) → Render Deploy Hook 호출 →
   `/health` 의 `commit` 이 방금 커밋과 같아질 때까지 최대 15분 기다리고, `persistent:true`(영속 DB)인지도 본다.

Render 는 포크 main 을 따라가지만 자동 배포가 꺼져 있어(`autoDeploy: false`) Deploy Hook 이 유일한 배포 길이다.
`render.yaml` 은 **참고용**이다 — 이 서비스는 대시보드에서 직접 만든 것이라 Start Command·환경변수 등은 대시보드 값이 정본이다.

**운영 메모**

- **Rollback 금지(2026-10-23 부터)**: Render 대시보드의 Rollback 으로 옛 리비전을 띄우면 그 리비전은 종료된 옛 모델을 부른다.
  문제가 생기면 되돌리는 커밋(revert)을 만들어 같은 배포 경로로 내보낸다.
- **환경변수(Render 대시보드 Environment)**: `DATABASE_URL`(Neon), `OPENAI_API_KEY`(매핑·판 4 심판), `ANTHROPIC_API_KEY`(서술), `PYTHON_VERSION`.
  판 4 를 켤 때 운영자 알림을 받으려면 `JUDGE_ALERT_WEBHOOK_URL`. **`JUDGE_CRITERIA_LOCK` 은 운영에 두지 않는다**(§14.8).
  서술만 문제가 생기면 `ANTHROPIC_API_KEY` 를 지워 규칙 문장으로 돌린다. 키가 들어 있는지·어떤 모델인지는 `/health` 의
  `llm.narrative`·`llm.mapping`(`key`·`model`)으로 본다. 환경변수를 저장해도 서버가 다시 뜨지 않을 수 있으니 **Manual Deploy** 로 다시 띄운다.
- **기관 이름 바꾸기**: API 가 없으므로(§11) Neon SQL 편집기에서 한 번 직접 바꾼다 — 예:
  `UPDATE organization SET org_name = '리트머스' WHERE id = 1;`(운영 DB 에는 2026-10-23 에 이미 적용). 이미 발급한 성적서의
  `issuance.issuer`(발급 당시 발급자 문자열)와 보관본은 바꾸지 않는다 — 발급 당시 그대로가 맞다.
- **새 표**: `narrative_jobs` 처럼 새 표는 기동 때 `create_all` 이 알아서 만든다. 이미 있는 표에 열을 더하는 것은 하지 못하므로
  (마이그레이션 도구 없음, §7 규칙 4) 스키마를 늘릴 때는 새 표로 한다.
- **판 4 를 켤 때는 백엔드가 먼저**: 프론트가 판 4 를 켜기(Vercel 환경변수) 전에 판 4 를 아는 백엔드가 운영에 떠 있어야 한다. `/health` 의 `commit` 으로 확인한다. 이유는 §13.
  그 백엔드에는 검증을 마친 기준의 기록(`app/judge/validated.json`, §14.8)이 들어 있어야 한다 — 없으면 판 4 성적서가 모두 발급 보류다.
- **판 4 발급 보류 찾기**: 서버 로그에서 머리말 `[심판 알림]` 을 찾는다. 작업마다 심판 한 줄 요약도 로그에 남는다(판정·회차·비용·시간·기준 버전, §14.5).
- **콜드 스타트**: Render 무료는 한동안 요청이 없으면 잠들고, 깨어나는 데 30~60초쯤 걸린다. 시연 전에 `/health` 를 한 번 불러 깨운다.
- **Neon 연결 문자열**: `sslmode=require` 를 둔다. 연결 때 `channel_binding` 옵션 오류가 나면 그 옵션만 빼면 된다.

## 13. 성적서 판 4 — 서술 요청의 판 신호 · 평가 엔진 버전 · 정답 폴더 (2026-10, 판 4 구현 라운드)

한 줄 요약: **판은 프론트가 정하고, 백엔드는 서술 요청에 실린 `report_edition` 하나만 본다.** 평가 API 는 판을 모르고, 판 4 에 필요한 새 값을 늘 응답에 더해 보낸다.

### 13.1 성적서 판

판(contentSchema)은 프론트가 성적서 데이터에 찍는 번호다. 발급 보관본(`report_snapshot.content_json`)에도 그대로 들어 있고, 번호로 열 때 프론트가 찍힌 판의 모양으로 다시 그린다.

| 판 | 무엇 |
|---|---|
| 1 | 판 표시가 없는 옛 발급본 |
| 2 | 서술 라운드 앞 dev 의 모양(운영에는 배포되지 않음) |
| 3 | 지금 기본값. 7·8·9절 서술(§10 의 칸 이름이 이 판의 번호다) |
| 4 | 목차를 1 시험 개요 · 2 시험 대상 · 3 시험 방법 · 4 시험 결과 · 5 분석 소견 · 6 개선 권고로 다시 묶은 판. 프론트 빌드 플래그로 켠다. 운영에서는 아직 켜지 않았다 |

- 판은 프론트가 run 을 만들 때 한 곳(`newRunContentSchema()`)에서 정한다. 켜는 법·켜기 전 확인 목록은 프론트 저장소 `docs/ARCHITECTURE.md` §6.6.
- 백엔드에는 판 플래그(환경변수)가 없다.

### 13.2 서술 요청의 판 신호 `report_edition`

- `NarrativeRequest`(`narrative/schemas.py`) 최상위 칸 `report_edition: Literal[3, 4] = 3`. 판 3 요청에는 이 키가 없고(기본 3), 판 4 run 의 요청에만 `4` 가 실린다. 3·4 밖의 값은 422. `fact_sheet.facts` 안에 두지 않는 이유는, facts 는 형식이 틀리면 통째로 버려질 수 있어서다(`jobs._soft_kind`).
- 기본값 3 은 요청 경계(`NarrativeRequest`)와 옛 경로 입구(`legacy.py` 의 `EDITION = 3`)에만 있다. 안쪽 함수(`build_fact_view`·`build_number_whitelist`·`select_items`·지시문·`checks`·`fallback`·`baselines` 등)는 기본값 없는 keyword-only `edition` 으로 받는다 — 한 곳을 빠뜨리면 바로 오류가 난다. 작업 경로에서는 `jobs.create_job`(바로 돌려주는 참조 범위 표)과 `generator` 가 요청의 값을 읽어 하위 호출에 넘긴다.
- 판 4 에서 달라지는 것:
  - 사실 시트 보기 `fact_view_ed4.py`(판 3 보기 `fact_view.py` 는 그대로) — 숫자는 판 4 표기, 판정 여유, 통과율 없음, 참조 범위는 위치만.
  - 숫자 표기 `wording_ed4.py` — 셋째 자리·끝 0 유지, 판정과 어긋나 보이면 여섯째 자리까지 늘림. 규칙은 두 저장소 공통 대조 표 `tests/contract/number_wording_ed4.json`(프론트 `src/test/contract/` 와 같은 바이트)에 있다.
  - 지시문(`prompt.py` 판 4 system)·숫자 검문(`grounding.py` 판 4 허용 목록과 판 4 절 번호)·규칙 문장(`required_items.py`·`fallback.py`)·출처 글(`baselines.py`). 칸은 같은 일곱 칸이고 자리만 판 4 번호(8.2 → 5.1, 9.1 → 6.1 등, `sections.place`)다.
  - 문제 종류 `same_source`(평가 데이터가 학습과 같은 출처)와 그 규칙 권고 — 판 4 요청에만 온다.
  - 판 4 작업은 서술을 만든 뒤 심판이 검사하고(`jobs.run_job_ed4`), 결과에 고객용 심판 묶음 `judge` 가 붙는다. 판 4 요청에는 심판 읽기 재료 `judge_material` 이 실린다(서술 생성은 읽지 않는다). §14.
- 옛 경로(`/api/generate-narrative`, `legacy.py`)는 `report_edition` 을 읽지 않고 늘 판 3 이다. 사실 시트를 통째로 지시문에 넣으므로 판 4 전용 칸은 빼고 넣는다(`EDITION4_ONLY_SHEET_FIELDS`).
- 계약 사본: 판 4 명세 `tests/contract/fact_sheet_contract_ed4.json`, 칸→자리 대응표 `narrative_slots_ed4.json`, 이진·다중·멀티 예시 `fact_sheet_{binary,multiclass,multilabel}_ed4.json`. 예시는 프론트가 앱이 실제로 보낸 요청을 떠서 만든다. 프론트 사본과 같은 바이트여야 하고(옆 저장소가 있을 때만 대조 — CI 는 이 저장소만 받는다), 고칠 때는 두 저장소와 sha256 을 함께 고친다.

**왜 백엔드를 먼저 배포하나** — 옛 백엔드가 판 4 요청을 받으면:
- `report_edition` 을 모르는 칸이라 오류 없이 버린다(pydantic 기본 동작) → 판 4 성적서에 판 3 절 번호·표기의 서술이 들어간다.
- 문제 종류 `same_source` 를 몰라 요청을 422 로 돌려보낸다(`problems` 는 facts 밖이라 버려지지 않는다).
- 멀티레이블 `facts.distribution_shift_status` 의 새 값 `training_samples_not_provided` 를 몰라 facts 를 통째로 버린다.

그래서 판 4 를 켜는 라운드에는 이 저장소를 먼저 배포하고 `/health` 의 `commit` 을 확인한 뒤 프론트 플래그를 켠다.

### 13.3 평가 응답에 더한 값

평가 API(`/api/evaluate`)는 판을 모른다. 아래 값은 늘 계산해 보내고, 판 3 프론트는 읽지 않는다. 기존 칸의 값과 반올림(넷째 자리)은 그대로다.
- `EvaluateResponse` 최상위: `source_file{sha256, size_bytes}`(업로드 파일 해시·크기, `environment.source_file_info`), `engine_version`.
- 프론트가 아는 키만 골라 읽는 객체 안: 신뢰구간 `low_raw`·`high_raw`(반올림 전 경계), F1 최대 임계값(`f1_threshold_gain`)의 그 점·지금의 Recall·Precision과 반올림 전 값(`*_raw`), 임계값 표기 `best_threshold_text`(셋째 자리부터 늘려 가며, 그 표기를 실제로 적용해도 예측이 같은 가장 짧은 자릿수 — 예: 0.6166), 불균형 영향의 반올림 전 값.
- `environment`·`derived_prediction`·클래스 리포트(M22)·분포·`warnings` 안에는 새 키를 두지 않는다 — 프론트가 이 객체들을 통째로 저장해 판 3 데이터에 키가 생기기 때문이다.

### 13.4 평가 엔진 버전 올림 규칙

- 위치: `app/evaluation/environment.py` 의 상수 `ENGINE_VERSION`(첫 값 `"1.0.0"`). 평가 응답 `engine_version` 으로 나가고, 판 4 성적서 3.5 "평가 엔진 버전" 칸에 그대로 찍힌다. 환경변수로 받지 않는다 — 배포 설정 없이 부팅되고 로컬·CI·운영이 같은 값을 낸다.
- **올린다**: 같은 입력 파일·요청이 다른 평가 값을 낼 수 있게 되는 변경. 예: 지표 계산식, 반올림·표시 자릿수 규칙, 신뢰구간 방법, F1 최대 임계값·임계값 표기를 고르는 규칙, 불균형 영향 계산, 평가에 들어갈 행을 정하는 규칙(`frame.py`)·클래스 표기·파싱이 바뀌어 값이 달라지는 경우. 라이브러리를 올려 `tests/golden_ed4` 정답 값이 바뀌었다면 이것도 계산이 바뀐 것으로 본다.
- **그대로 둔다**: 주석·문서, 기존 값을 바꾸지 않는 응답 칸 추가, 서술·발급 쪽 변경.

## 14. 판 4 심판 — 서술 검사 · 발급 보류 · 기준 묶음 · 검증 도구 (2026-10, 심판 라운드)

한 줄 요약: **판 4 서술은 다 만든 뒤 다른 회사 모델(OpenAI)이 한 번 더 읽어 검사하고, 통과해야만 인쇄·발급할 수 있다.**
걸리면 문제 칸을 다시 만들거나 규칙 문장으로 바꿔 다시 검사하고, 그래도 안 되면 "발급 보류"로 끝난다. 판 3 은 심판이 돌지 않는다.

비유하면 서술 생성기(Claude)가 쓴 글을 따로 선 검수자(심판)가 데이터 원본과 맞대 보는 것이다. 검수자는 글을 고치지 않고
"어느 칸이 틀렸다"만 알린다. 고치는 일(다시 만들기·규칙 문장)은 서술 쪽이 한다.

### 14.1 언제 도나

- **판 4 작업만**: 서술 요청의 `report_edition` 이 4 인 작업(§13.2)이 `jobs.run_job_ed4` 로 돈다. 판 3 작업(`run_job`)과 옛 경로는
  심판을 부르지 않고, 판 3 결과·내부 기록에는 심판 키가 하나도 없다.
- **순서**: 생성(판 3 과 같은 생성기) → 심판 사다리(14.3) → 고객용 심판 묶음을 결과에 붙여 끝 상태 쓰기 → 보류·실패면 운영자 알림.
  채점 중에는 작업 단계가 `judging`("검증 중")이다(판 4 작업에만 있는 단계).
- **시간은 서술 작업과 같은 10분 마감 하나**(`JOB_DEADLINE_SECONDS`). 생성은 `ED4_GENERATION_SECONDS` 안에서 끝내고, 채점은 끝 상태를
  쓸 여유를 뺀 `JOB_GENERATION_SECONDS` 까지 쓴다. 채점 하나를 시작하려면 최소 `ladder.JUDGE_MIN_SECONDS` 가 남아 있어야 한다.
  채점이 길어 유실(§10.7)로 오인되지 않게 채점 중에는 `JUDGE_HEARTBEAT_SECONDS` 마다 단계를 다시 쓴다.
- **심판 키·지갑은 만들 때 먼저 본다**: 심판 클라이언트는 매핑과 같은 `OPENAI_API_KEY` 의 OpenAI 클라이언트다(`app.state.openai_client`).
  키가 없거나(no_key)·검증 기록 잠금(14.8)에 걸렸거나(보류 judge_error)·심판 지갑(`JUDGE_REPORTS_PER_HOUR`)이 비었으면(budget)
  **서술 AI 도 부르지 않고** 규칙 문장 서술 + 발급 보류로 끝낸다 — 검사하지 못할 글에 생성 비용·심판 지갑을 쓰지 않게(순서: 키 →
  잠금 → 지갑). 작업 행 상한(job_limit)도 판 4 면 보류 묶음을 붙인다.
- **동시 채점 수**: 채점 한 번이 칸 하나(`JUDGE_SLOTS`, 서술 칸과 따로). 칸을 `JUDGE_SLOT_WAIT_SECONDS` 안에 얻지 못하면 보류(busy).

### 14.2 채점 한 번 (`core.judge_once`)

채점은 주어진 서술을 **검사만** 한다(생성 없음). 사다리·작업 흐름·검증 실행기·파일럿이 모두 이 함수 하나를 쓴다.

1. **읽을 재료 모으기**(`material.py`·`reading.py`): 성적서에 실제로 찍힌 글을 "조각"으로 모은다. 조각 출처는 넷 — `ai`(AI 칸)·
   `template`(규칙 문장 칸)·`fixed`(고정 문구)·`table`(표). AI·규칙 문장 글은 백엔드가 생성 결과로 갖고 있고, 프론트가 찍는 고정
   문구·표는 프론트가 서술 요청의 `judge_material` 에 **화면과 같은 글자로** 실어 보낸다(계약 `tests/contract/judge_material_ed4.json`).
   4.6 참조 범위 표는 백엔드가 만든다. 재료가 없거나 모양이 틀리거나, 조회 자료(혼동행렬 건수·클래스별 표)가 비었으면 채점하지
   않고 보류(no_material). 재료 칸은 서술 생성 지시문에 들어가지 않는다.
2. **공용 전처리 — 주장 추출**(`extract.py`, 모델 `gpt-6-luna`·추론 강도 low): AI·규칙 문장 조각에서 사실 주장(숫자·비교·이름·정도·
   추론)을 인용 구절과 함께 뽑는다. 빠진 주장을 같은 모델에 최대 2번 더 묻는다(자기 점검). 인용이 그 조각에 없는 주장은 버리고,
   숫자가 있는데 주장이 0개면 실패(no_claims).
3. **4축을 따로 잰다** — 모델 `gpt-6.1-sol`, 추론 강도 medium. 넷은 서로의 결과를 보지 않는다.

| 축 | 무엇을 | 방식 | 읽는 범위 | 게이트 |
|---|---|---|---|---|
| 사실 일치 `faithfulness.py` | 주장이 데이터(사실 시트·파생값·고객 입력·4.6 표)와 맞나 | 칸이 정해진 숫자 주장은 코드가 바로 대조. 나머지는 도구 4개를 쓰는 에이전트가 **대상 칸·식만** 찾고, 맞다·틀리다는 코드가 계산해 정한다 | AI·규칙 문장 | 위반·단정형 추론 1건 이상이면 막음 |
| 필수 내용 `coverage.py` | 꼭 다룰 항목이 글에 있나 | 적용 항목은 코드가 고르고(기준 묶음 `checklist.json`), LLM 은 있다/없다 + 인용. 인용이 표에만 있으면 "없음". **고객 묶음에서 뺀 축**(2026-11-01 — 검증 결함 D03 미달): 내부 기록으로만 돌고, 실패·인용 문제로도 보류하지 않는다 | 전부 | 아님 |
| 일관성 `consistency.py` | 같은 값이 다르게 찍혔나, 글끼리 모순이 있나 | 값 불일치는 코드(같은 칸의 찍힌 숫자 비교), 논리 모순 3유형(판정↔권고, 약점↔권고, 분석↔소견)은 LLM — 두 구절 인용 필수 | 전부 | 모순 1건 이상이면 막음 |
| 표기 `readability.py` | 영어 코드값 노출·서술체·어법 | 코드 규칙 2개(로마자 노출, 해라체·글머리 기호) + LLM 어법 판정 | AI·규칙 문장 | 아님 |

4. **합산과 게이트**(`aggregate.py`, LLM 없음): 축마다 "검사 n건 중 m건"처럼 분모를 함께 낸다. 종합 점수는 만들지 않는다.
   게이트는 **사실 위반(단정형 추론 포함) ≥ 1 또는 모순 ≥ 1 이면 blocked**, 아니면 pass. 필수 내용·표기는 게이트가 아니다.
   걸린 칸: 사실 위반은 그 주장의 칸, 모순은 서술 칸 쪽(둘 다 서술 칸이면 7.1 → 9 순서의 뒤쪽). 둘 다 표·고정 문구면 고칠 칸이
   없다(unfixable).
5. **안전장치**(`safety.py`): 합산 전에 모든 위반·모순·"서술됨" 판정의 인용이 실제로 그 조각 글에 있는지 한 번 더 본다. 하나라도
   어긋나면 그 채점을 쓰지 않고 보류(safety).
6. 어느 모듈이든 호출이 실패하면(시간 초과·거절·형식 오류·인용 없음 등) 게이트 없이 실패로 끝난다 — **실패가 통과로 새지 않는다.**

- **OpenAI 호출 한 곳**(`judge/llm.py`): Responses API, 응답 보관 끔(`store=False` — 서술 글·사실 값이 OpenAI 쪽에 남지 않게),
  온도·seed 없음, SDK 재시도 끔. 일시적 오류(429·5xx·연결 끊김)만 남은 시간 안에서 한 번 더. 비용은 응답 모델 단가(`config.PRICES_PER_MTOK`)로
  세고, 단가를 모르면 None(추정하지 않는다).
- **import 규칙**(`tests/test_judge_import_rules.py`): 서술 생성 쪽 모듈(지시문·생성기·검문·결론 목록·사실 시트 보기·규칙 문장·
  표기)은 `app.judge` 를 import 하지 않는다 — 작업 흐름(`jobs.py`)만 심판을 부른다. 거꾸로 `app.judge` 는 서술 쪽 판정 규칙
  (`checks`·`grounding`·`required_items`)을 import 하지 않는다 — 서술 검문을 고치면 심판 기준이 몰래 바뀌기 때문이다. 필요한 작은
  도구는 기준 묶음(14.6)에 복사해 둔다. **심판 사유·인용은 생성 쪽으로 넘기지 않는다** — 다시 만들기에는 칸 이름만 넘긴다.

### 14.3 발급 보류 사다리 (`ladder.py`)

```
채점 1 ─통과→ 끝(passed)
  └ 걸림 → 걸린 칸 AI 로 다시 만들기(작업당 한 바퀴) → 채점 2 ─통과→ 끝
                 └ 걸림 → 걸린 칸 규칙 문장 → 채점 3 ─통과→ 끝
                            └ 걸림 → 서술 칸 전부 규칙 문장 → 채점 4 ─통과→ 끝
                                       └ 걸림 → 발급 보류(gate_failed)
```

- 이미 규칙 문장·고정 문구인 칸은 다시 만들지 않는다. 7.3 은 규칙 문장이 없어 비우고 "해당 없음"이 찍힌다.
- 한 단이 아무 칸도 바꾸지 못하면 같은 글을 다시 채점하지 않고 다음 단으로 간다. 마지막 단도 바꿀 것이 없으면 보류.
- 남은 시간이 "다시 만들기(`REGENERATE_MIN_SECONDS`) + 채점(`JUDGE_MIN_SECONDS`)"에 모자라면 다시 만들기 단을 건너뛰고 규칙 문장 단으로.
  채점할 시간조차 없으면 보류(timeout).
- 재채점은 늘 서술 전체다. 채점이 실패하면 그 자리에서 보류한다.

### 14.4 보류 종류와 "서술 다시 만들기"

보류 종류와 다시 만들기 허용은 `ladder.held_kind`·`ladder.retry_allowed` 두 함수가 정한다(작업 흐름의 키 없음·지갑·행 상한·바깥 시간
초과도 이 함수를 부른다). 종류 목록은 `ladder.HELD_KINDS` 이고 고객 묶음 계약과 같은 집합이다(시험이 맞댄다).

| 보류 종류 | 언제 | 다시 만들기 |
|---|---|---|
| `gate_failed` | 사다리를 다 타고도 사실 위반·모순이 남음 | 없음 |
| `timeout` | 채점할 시간이 모자람, 또는 서술이 생긴 뒤 10분 마감을 넘음 | 게이트에 한 번도 걸리지 않았을 때만 |
| `judge_error` | 심판 호출 실패·거절·형식 오류·안전장치·예기치 않은 예외·기록 직렬화 실패·검증 기록 잠금(14.7) | 게이트에 한 번도 걸리지 않았고 일시적 사유(호출 시간 초과·5xx·429·연결 끊김·슬롯 대기 초과)일 때만 |
| `no_key` | 심판 키(OpenAI)가 없음 | 없음 |
| `budget` | 심판 지갑 소진 | 늘 있음(한 시간쯤 뒤) |
| `job_limit` | 작업 행 시간당 상한 — 행 없이 바로 규칙 문장 결과 | 없음 |
| `no_material` | 심판 읽기 재료가 없거나 틀림(요청 크기 예산으로 빠짐 포함), 조회 자료가 빔 | 없음 |

- 판 4 작업에서 서술이 생기기 전에 10분을 넘으면 판 3 과 같은 실패(failed·timeout)다. 서술이 생긴 뒤 넘으면 완료 + 보류(timeout).

### 14.5 고객 묶음과 내부 기록

- **고객용 묶음**(조회 응답 `result.judge`, `bundle.py`, 계약 `tests/contract/judge_bundle_ed4.json` — 프론트와 같은 바이트):
  `gate`(passed·held), `held_kind`, `retry_allowed`, `criteria_version`(점검 기준 버전), `model`(요청한 심판 모델 이름), `axes`(싣는 축 목록 —
  `bundle.PUBLISHED_AXES` 한 곳, 지금은 사실 일치·일관성·표기 셋), `counts`(passed 일 때만 — `axes` 에 든 축의 검사·결과 건수만, 뺀 축은
  키째 없다). **근거 인용·
  판정 사유·주장 목록·재생성 횟수·토큰·비용·시간·기준 지문은 싣지 않는다** — 번호만 알면 열리는 응답이기 때문이다. 판 3 결과에는
  `judge` 키가 없다.
- **내부 기록**(`internal_json["judge"]`): 판정·보류 종류·실패 사유, 채점 회차마다 걸린 칸·점수표·모듈별 결과·호출 기록(토큰·비용·
  시간), 다시 만든 칸·규칙 문장으로 바꾼 칸, 심판 지갑 상태(`judge_budget`), 잠금 상태(`criteria_lock`: ok·off·잠금 사유), 한 줄
  요약(`summary` — 서버 로그에도 한 줄), 통과했으면 **서술 글 지문**(`narrative_sha256`, 14.6). 판 4 작업 내부 기록 최상위에는
  `report_edition: 4` 가 있다.
- **운영자 알림**(`alert.py`): 서버 로그 한 줄(머리말 `[심판 알림]`) + 환경변수 `JUDGE_ALERT_WEBHOOK_URL` 이 있으면 그 주소로 POST.
  판 4 발급 보류(held)·판 4 생성 실패(failed), 그리고 조회 때 유실로 판정한 작업(lost — 판과 관계없이)에 작업당 한 번. 작업 번호·
  종류·짧은 사유만 싣고 서술 글·인용·고객 입력은 싣지 않는다. 웹훅은 몇 초 제한·재시도 없음이고, 실패해도 작업 상태를 바꾸지 않는다.

### 14.6 서버 발급 검사 (`issuance/judge_gate.py`)

화면 잠금(프론트)만으로는 옛 화면·직접 호출을 막지 못하므로, 서버가 판 4 성적서의 **첫 발급과 정정 발급** 모두에서 다시 본다.
요청 칸 `narrative_job_id`(서술 작업 번호)가 "판 4 · 완료 · 심판 통과"인 작업이어야 받는다.

- **판 판정**(프론트 `reportLock.isEdition4Content` 와 같은 닫힌 쪽 규칙): `content` 가 없거나 `contentSchema` 가 없으면 판 1 로 보고 검사하지
  않는다(CI 발급 스모크 `{"smoke": true}` 가 여기). 정수 1·2·3 이면 검사하지 않는다. 그 밖의 값(4, "4", 4.0 …)은 모두 판 4 로 검사한다.
- **서술 글 지문 대조**(`narrative/digest.py`): 통과한 작업의 서술 글 지문(`internal_json.judge.narrative_sha256`)과 `content` 안 서술
  글로 만든 지문을 맞댄다 — "통과한 다른 작업 번호"를 붙이거나 서술을 바꾼 `content` 를 막는다. 지문은 프론트가 작업 응답을
  성적서 데이터로 옮기는 규칙(빈 칸은 "", 우선순위는 대문자·모르면 MEDIUM 등)을 흉내 낸 모양의 sha256 이고, 글자는 바이트 그대로
  본다(공백·유니코드 정규화 없음). 규칙은 `digest.py` 머리에 있다 — 프론트의 옮기는 규칙이 바뀌면 함께 고친다.
- **거절 사유 코드**(거절마다 다름, HTTP 409, 글 끝 괄호에 코드). 고객에게 보이는 글(`judge_gate.MESSAGES`)은 사용자가 정한
  쉬운 문안(합니다체, 2026-10-29)이고 내부 낱말("심판"·"판 4"·AI·LLM·모델 이름)을 쓰지 않는다 — 시험
  (`test_issuance_messages_have_no_internal_words`)이 지킨다. 프론트 시험 `src/hooks/judgeHeld.test.tsx` 가 `judge_not_passed` 글을
  그대로 박아 두었으니 글을 바꾸면 함께 고친다(다른 프론트 시험은 자리 글 "보류"·"글" 만 쓴다).

| 코드 | 뜻 |
|---|---|
| `judge_job_missing` | 작업 번호가 없음 |
| `judge_job_not_found` | 그 번호의 작업이 없음 |
| `judge_job_not_edition4` | 판 4 작업이 아님 |
| `judge_record_expired` | 작업 기록 보관 기간(`NARRATIVE_JOB_RETENTION_DAYS`)이 지남 |
| `judge_not_passed` | 진행 중·실패·보류 |
| `judge_narrative_unrecorded` | 통과 기록에 서술 글 지문이 없음 |
| `judge_narrative_mismatch` | `content` 의 서술 글이 그 작업의 글과 다름 |
| `judge_criteria_unverified` | 통과 기록이 검증 기록 잠금을 거치지 않음 — `judge.criteria_lock` 이 `"ok"` 가 아니고, `"off"` 인데 지금 잠금이 켜져 있거나, 값이 없음(14.8) |

- **잠금 값 확인**: 통과 기록의 `judge.criteria_lock` 이 `"ok"`(검증한 기준으로 채점)면 받는다. `"off"`(잠금을 끈 시험·개발 서버에서 채점)는
  **지금도 잠금이 꺼져 있을 때만** 받는다 — 운영은 잠금을 끌 길이 없으니 닫힌 쪽이고, 개발 스모크는 그대로 된다.
- 짝 없는 대리 글자(JSON 의 `"\ud800"`)가 든 서술도 지문은 만들어진다(예외 없이 `judge_narrative_mismatch`). API 앞단(요청 JSON 검증)에서 걸리면
  앱 전역 422 처리기(`app.main.request_validation_error`)가 500 없이 422 로 돌려준다(오류 목록의 대리 글자는 `\uXXXX` 이스케이프). `problem_id` 앞뒤 공백은
  자바스크립트 `trim` 과 같은 글자 집합(`digest.JS_TRIM`)으로 뗀다.

- 작업 행 상한(job_limit)으로 행 없이 끝난 판 4 결과는 작업 번호가 없어 발급 검사를 통과할 수 없다(보류 그대로).
- 프론트는 모르는 `judge_*` 코드도 "서버가 발급을 거절했습니다: {서버 글}"로 보인다 — 코드를 더해도 화면 글을 고칠 필요가 없다.

### 14.7 기준 묶음 `app/judge/criteria/` 와 버전

심판이 **무엇을 어떻게 재는지** 정하는 파일 전부를 한 폴더에 묶고 지문으로 고정한다 — 체크리스트(`checklist.json`)·주장 규칙
(`claims.json`)·모순 유형(`contradictions.json`)·정도 표현(`degree.json`)·이름 표(`names.json`)·표기 규칙(`readability.json`)·판정
기준값(`rule_constants.json`)·모델 설정(`model.json` — 심판·전처리 모델, 추론 강도, 사실 일치 에이전트 최대 회차)·프롬프트(`prompts/`)·
작은 코드 규칙(`rules_*.py`)과 로더(`__init__.py`).

| 파일 | 뜻 |
|---|---|
| `MANIFEST.sha256` | 묶음 파일마다 sha256. 이 글 전체의 sha256 이 **기준 지문**이다 |
| `VERSION` | 지금 버전. 고정 전에는 `1.0-dev` 처럼 `-dev` 가 붙는다 |
| `VERSIONS.json` | 고정한 버전 → 지문 기록. **덧붙이기만** 한다 |
| `CHANGELOG.md` | 무엇을 왜 바꿨는지. 버전마다 `## <버전>` 절 |

`MANIFEST.sha256`·`VERSIONS.json`·`CHANGELOG.md` 자신은 지문에 들지 않는다(설명 글을 고쳐도 기준은 같다).

- **기준 파일을 고칠 때**: 같은 커밋에서 `venv/bin/python scripts/judge_criteria_manifest.py`(= `write`)로 MANIFEST 를 다시 쓰고, 이유를
  CHANGELOG 에 적는다. 시험(`tests/test_judge_criteria_manifest.py`)이 파일 ↔ MANIFEST, 버전 기록 ↔ 지금 지문을 맞대서, 몰래 바꾸면 빨개진다.
- **고정(freeze)**: `venv/bin/python scripts/judge_criteria_manifest.py freeze 1.0` — VERSION 을 그 버전으로 바꾸고 MANIFEST 를 다시 쓴 뒤
  `VERSIONS.json` 끝에 "버전 → 지문"을 덧붙인다. 버전 꼴이 "숫자.숫자"가 아니거나, 이미 기록된 버전이거나, 파일과 MANIFEST 가 다르거나,
  CHANGELOG 에 그 버전 절이 없으면 아무 파일도 바꾸지 않고 거부한다. 끝나면 시험에 덧붙일 줄과 태그 명령(`judge-criteria-v<버전>`)을
  찍는다 — 태그는 사람이 붙인다.
- **고정 뒤에 하나라도 바꾸면 버전을 올리고 다시 검증한다.** 고정한 버전의 지문은 바뀌면 시험이 빨개지고, MANIFEST 만 다시 써도 기록과 달라
  빨개진다. 다시 돌 범위는 `judge_validate.py rescope`(14.9)로 본다.
- `claims.json`(주장 규칙)은 사람 정답지 표시의 기준이라 sha256 을 시험에 따로 잠가 두었다(`CLAIMS_LOCK`). 바꾸면 정답지 표시도 다시 한다.

### 14.8 검증 기록 잠금 (`criteria_lock.py`)

"운영에 나가는 기준 = 검증을 마친 기준"을 코드로 지킨다. 검증을 마친 기준의 버전·지문을 `app/judge/validated.json` 에 적고(기준
묶음 폴더 **밖** — 안에 두면 기록을 쓰는 순간 지문이 바뀐다), 판 4 작업은 심판을 부르기 직전에 **지금 파일로 다시 만든** 지문이
이 기록과 같은지 본다. 작업을 **만들 때 한 번**(잠기면 서술 AI·심판 지갑을 쓰지 않는다 — 14.1) 보고, 심판 갈래에서 **한 번 더** 본다(두 겹).
지금 기록: 기준 **1.25**(2026-11-01, 부분 검증 — 재현성 통과·결함 2/3 탐지·필수 내용 축 뺌·추출 미달, 민서 결정으로 수용. 자세한 것은
기록의 `note`). 기준을 바꾸면 이 기록도 함께 고쳐야 한다 — 시험 `test_repo_record_matches_the_current_criteria` 가 지킨다.

```json
{"version": "1.0", "fingerprint": "<지금 파일로 만든 MANIFEST 글의 sha256>", "tag": "judge-criteria-v1.0", "validated_at": "…", "note": "…"}
```

- 판정에 쓰는 것은 `version`·`fingerprint` 둘뿐이다(나머지는 사람이 읽는 기록). 서버에서 기준 파일 하나가 몰래 바뀌어도 잡힌다.
- 기록이 없음(unvalidated)·읽을 수 없음·지금 버전이 `-dev`·버전이나 지문이 다름이면 **심판을 부르지 않고** 보류(judge_error, 다시 만들기
  없음 — 다시 만들어도 같은 기준이라 풀리지 않는다). 사유는 내부 기록 `judge.criteria_lock` 과 서버 로그에만 남는다.
- **실제로 쓰일 모델·추론 강도도 본다**(model_mismatch): 환경변수(`JUDGE_MODEL`·`JUDGE_EXTRACT_MODEL`·`JUDGE_EFFORT`·`JUDGE_EXTRACT_EFFORT`)까지
  반영한 값(`app.judge.config`)이 `criteria/model.json` 과 하나라도 다르면 잠긴다 — 검증하지 않은 모델로 채점해 통과로 나가지 않게. 무엇이
  달랐는지는 내부 기록 `judge.model_drift`(`{칸: {"criteria": …, "actual": …}}`)에 남는다. 잠금이 꺼져 있으면 잠그지 않고 기록만 한다.
- 발급 검사(14.6)는 통과 기록의 `criteria_lock` 값을 다시 본다(`"ok"`, 또는 지금도 꺼진 상태의 `"off"` 만).
- **기록 파일은 검증을 마친 뒤에 쓴다.** 그 전에는 기록이 없으므로 판 4 작업은 늘 보류다 — 판 4 를 켜기 전 확인 목록의 한 줄이다.
- **잠금은 늘 켜져 있다.** 끄는 길은 환경변수 `JUDGE_CRITERIA_LOCK=off` 하나뿐이고(대소문자·앞뒤 공백만 너그럽게, 그 밖의 값은 모두
  켜짐), pytest 장치(`tests/conftest.py`)와 가짜 LLM 개발 서버(14.10)만 쓴다. **운영(Render)에는 절대 두지 않는다.** 꺼진 상태도 내부
  기록(`criteria_lock: "off"`)과 경고 로그로 남는다.

### 14.9 검증 도구 (사람이 직접 실행 — pytest 가 아님)

심판을 운영에 내기 전에 "같은 글에 같은 판정을 내나(재현성), 심어 둔 결함을 잡나, 뜻이 같은 글을 같게 보나(sham), 주장을 빠짐없이
뽑나(추출 재현율·정밀도), 사람과 판정이 맞나(일치도)"를 재는 도구다. 계산은 `app/judge/validation/` 의 순수 함수가 하고, 스크립트는
그 함수를 부르는 얇은 층이다. 앱 실행 경로는 이 모듈을 import 하지 않는다.

| 모듈 | 하는 일 |
|---|---|
| `runs.py` | 묶음 넷(`reproducibility`·`defects`·`sham`·`extraction`)의 회차 계획·이어 하기·순서 섞기. 기본 회차는 `DEFAULTS`(아래 "기본 회차"), 기본 성적서는 `DEFAULT_REPORTS` |
| `variants.py` | 결함본·sham 폴더 꼴(`meta.json`·`slots.json`·`diff.txt`)과 적용 |
| `stats.py` | ICC·게이트 재현성·결함 탐지·독립성·sham·사람 일치 판정(기준값은 상수·인자 — 아래 "통과 기준") |
| `extraction.py` | 사람 정답지 주장 ↔ 시스템 추출 주장 일대일 짝짓기, 재현율·정밀도, 사람이 놓친 주장 판정표 |
| `agreement.py` | 카파·Gwet AC1 |
| `annotation.py` | 정답지 표 꼴(문장 표·주장 표) |
| `sheets.py` | 블라인드 사람 채점지·열쇠, 블라인드 읽기 묶음 |
| `rescope.py` | 바뀐 파일 → 다시 돌 모듈·묶음·사람 일치도 축 |

**`scripts/judge_validate.py`** — 검증 실행기. 레포 루트에서 `venv/bin/python scripts/judge_validate.py <하위 명령> --mode dev|verify …`.

- **두 모드**
  - `dev`: 가짜 LLM(심판 "문제 없음" 답)과 개발 입력(`tests/data/judge_dev` — 키 없이 규칙 문장 서술을 만든다)·합성 결함만으로 흐름을
    돈다. 결과는 임시 폴더. 읽고 쓰는 경로는 **허용 목록**(개발 입력·시스템 임시 폴더·`/tmp`·환경변수 `JUDGE_DEV_DIRS` 에 적은 폴더) 안이어야
    하고, 검증 폴더(환경변수 값과 저장소 옆 기본 자리 둘 다) 안이면 열기 전에 거부한다(오염 방지) — 장부·입력·결함·출력·정답지·사람 채점,
    장부가 가리키는 결과 원본 경로까지. 경로 비교는 `scripts/judge_paths.py` 한 곳(링크·`..` 를 풀고 유니코드 NFC·대소문자 무시 + 같은
    파일 확인 — macOS 의 자모 분해·대소문자 다른 철자 우회를 막는다). `judge_cost_report.py`·`judge_live.py` 의 봉인·검증 폴더 거부도 같은 함수.
  - `verify`: 진짜 검증. 다섯이 모두 맞아야 시작하고, 어긋난 사유를 하나씩 따로 찍는다 — ① 작업 트리가 깨끗함 ② 기준 버전이 고정 버전이고
    기록된 지문과 같음 ③ 지금 MANIFEST 가 태그 `judge-criteria-v1.0` 의 MANIFEST 와 같음 ④ `--live` ⑤ 장부에 쓸 수 있음.
- **검증 폴더**: 환경변수 `JUDGE_VALIDATION_DIR`(없으면 코드 `validation_root()` 의 기본 위치). 안의 하위 폴더 이름은 코드 상수다 —
  `00_봉인`(검증용 봉인 서술, `SHA256SUMS` 와 맞아야 함)·`01_정답지`(사람 주장 표시)·`02_결함`(결함본·sham)·`03_실행`(회차별 결과 원본)·
  `04_사람평가`(채점지·읽기표)·`05_결과`(report 결과), 장부는 `장부.csv`. 봉인 서술 글은 화면에 찍지 않는다(개수·해시·게이트만).
- **하위 명령**

| 명령 | 하는 일 |
|---|---|
| `run <묶음>` | 회차마다 장부 한 줄 + 결과 원본 파일 하나. 시작할 때 V2 전체 계획(채점 10회 ≈ $1.5)·이번 묶음 예상 회차·비용·장부 누계를 찍고 `--yes` 가 없으면 멈춘다. `verify` 재현성에서 `--reports` 를 주지 않으면 기본 3건. `extraction` 은 채점을 부르지 않는다(재현성 회차의 추출 기록을 쓴다) |
| `report` | 장부·결과 원본으로 판정값을 계산해 `검증결과.json`(verify 는 `05_결과`, dev 는 `--out`). 정답지·사람 채점이 있으면 추출 재현율·일치도·효용성도. 아래 "놓친 주장" |
| `check-defects` / `make-diff <변형>` | 결함본·sham 폴더 꼴 검사 / `diff.txt` 를 도구로 쓰기 |
| `sheets` | 사람 일치도 채점지(블라인드 — 시스템 판정·결함 여부·바탕 성적서 이름 없음, 문서 머리는 문서 번호뿐)·열쇠(따로, 해시, 읽기 전용)·읽을 문서. 층을 나눈 표본(`--n` 기본 40 = 축마다 10, `--overlap` 두 사람이 같이 채점할 문항 모두 기본 10 — 축마다 고르게 3·3·2·2, 후보가 모자란 축의 몫은 다른 축으로, `--seed`). 출력 폴더가 비어 있지 않으면 시작하지 않는다(먼저 만든 `읽기/` 만 둔다). 채점지 첫 줄(`# 열쇠 sha256: …`)과 `뽑기.json` 에 열쇠 해시 — report 가 열쇠 파일과 맞대 다르면 멈춘다 |
| `reading` | 블라인드 읽기 묶음 — 사람마다 문서(결함본은 심지 않은 사람에게만, **한 사람에게 한 성적서의 한 판본만** — 바탕본과 결함본을 같이 주지 않음)·빈 읽기표(첫 줄 열쇠 해시)·열쇠. 자리가 없는 결함본은 찍어 둔다(효용성 표의 "사람이 읽은 결함"에서 빠짐). 출력 폴더가 비어 있지 않으면 시작하지 않는다. report 가 효용성 표로 센다 |
| `rescope` | 재검증 범위 — `--changed <파일…>` 또는 `--since <커밋·태그>` 로 바뀐 파일을 주면 다시 돌 모듈·묶음·사람 일치도 축을 찍는다. 표에 없는 심판 코드, 그리고 표에 없어도 채점 입구(`app/judge/core.py`)에서 import 를 따라 닿는 `app/` 파일(예: `app/narrative/wording_ed4.py`)은 공통(전부 다시)으로 본다 |
| `status --ledger <장부>` | 장부 누계와 상한 |

  `verify` 에서 봉인 서술을 여는 명령(`check-defects`·`make-diff`·`sheets`·`reading`)은 기준 고정 뒤 사람이 `--allow-sealed` 를 줄 때만 돈다.
  `verify` 는 `--inputs`·`--defects` 를 받지 않는다(검증 폴더에서만 읽는다).
- **이어 하기**: 같은 모드·같은 기준 지문으로 결과 파일까지 적히고 **게이트 판정이 난**(pass·blocked) 회차는 건너뛴다 — 멈춘 뒤 같은 명령을
  다시 치면 이어 간다. 채점이 실패한 회차(게이트 빈칸)는 다시 돈다(실패 줄의 비용은 장부 누계에 남는다). report 도 회차마다 마지막 성공 줄만
  본다. 기준 지문이 달라지면(버전을 올린 재검증) 처음부터다. 남은 회차는 시드로 섞는다(`--seed`, 없으면 새로 뽑아 찍고 계획 파일·결과 원본에 남김).
- **기본 회차**(검증 결정 2026-10-29): 재현성 3건(`bc_strong`·`digits_weak`·`yeast_strong`) × 2회 = 6, 결함 3개 × 1회 = 3, sham 1 →
  채점 10회, 채점 1회 $0.15 로 약 $1.5. 추출 재현율·정밀도는 재현성 6회의 추출 기록을 쓴다(추가 비용 0). 회차는 인자로 바꿀 수 있다.
- **통과 기준**(검증 결정 2026-10-29 — `report` 가 이대로 센다)
  - 게이트 재현성: 3건 모두 2회 같은 판정(실패 회차가 있으면 같지 않다). 축 점수 ICC(A,1) 점추정 0.75 이상, 한 축의 모든 성적서·모든
    회차 점수가 같으면 그 축 통과(대상 2개·회차 2회 이상일 때만).
  - 결함 탐지: 결함 모두를 모든 회차에 탐지해야 통과(축 구분 없음, `stats.DETECTION_RULE = "all"`). 탐지 = 사실 일치·일관성은 심은
    문장을 인용한 위반, 필수 내용은 지운 항목이 "없음". 계획 결함 수(기본 3)보다 적게 돌았으면 계산 불가. 설계의 원래 기준(게이트 축은
    모든 회차, 그 밖 6개 중 5개가 5회 중 3회 이상)은 `rule="7.6"` 으로 남아 있다.
  - 독립성·sham: 결함을 심지 않은 축(sham 은 모든 축)의 점수 변화가 여유 이내. 여유 = max(바탕 성적서 회차 흔들림 폭, 최소 여유),
    최소 여유는 `stats.MIN_MARGIN` 한 곳 — 건수 축(일관성 모순 건수·표기 위반 건수) 1건, 비율 축(사실 일치 부합 비율·필수 내용 서술
    비율) 0.05.
  - 사람 일치: 시스템↔사람 일치율이 사람↔사람보다 한 문항 넘게 낮지 않음 — 여유 = 1 / 겹침 문항 수(10문항이면 10%p).
  - 표기 점수는 코드 규칙 위반 건수만 센다(LLM 어법 표시는 넣지 않는다).
  - 추출 짝짓기: 같은 칸·같은 문장(글자 범위를 알면 겹침)·숫자는 값 같음·일대일. 숫자·비교 주장은 같은 종류끼리만 짝이다. 정답지 주장
    표에는 대상 열이 없어 "대상 같음" 조건은 돌지 않는다(정답 쪽 대상이 늘 빈칸).
- **결함·sham 전 바탕 확인**: 결함본·sham 의 바탕 성적서마다 재현성 회차가 계획 회차(`--base-repeats`, 기본 `runs.DEFAULTS` = 2)만큼 끝났고
  모두 pass 여야 시작한다(흔들림 폭을 잴 바탕이 없으면 독립성·sham 을 셀 수 없다).
- **판정 세 값**: `report` 의 판정값은 통과·미달·**계산 불가**(`verdicts` 에 글로). 재현성 회차 수는 관측값이 아니라 계획값(`--reports-n`·
  `--repeats`, 기본 `runs.DEFAULTS`)으로 맞추고, 덜 돈 묶음은 계산 불가("덜 돎")다. ICC 분산 0 규칙(모두 같으면 통과)은 대상 2개·회차 2회
  이상일 때만 쓴다. 바탕이 다 돌지 않았거나 모두 pass 가 아니면 그 결함본·sham 의 독립성·sham 은 계산 불가다. 사실 일치 checked 0·필수
  내용 applicable 0(분모 0)이 그 성적서의 **모든 회차**면 그 성적서는 그 축에서 "해당 없음"(`not_applicable`)으로 빠지고 미달이 아니다.
  회차마다 다르면(어떤 회차만 0) 미달(`dropped`). 빠지고 남은 성적서가 2건 미만이면 그 축은 계산 불가 — 묶음의 축 판정도 계산 불가가
  된다. 독립성·sham 에서 바탕·비교 모든 회차가 분모 0 인 축도 해당 없음(변화 없음)으로 본다.
- **예산**: 묶음을 시작하기 전에 묶음 회차 상한(`--max-runs`, 기본은 `runs.DEFAULTS`)과 라운드 남은 상한(환경변수 `JUDGE_LIVE_BUDGET_USD`
  달러·`JUDGE_LIVE_MAX_RUNS` 회차, 장부 누계 포함. 없으면 `judge_live.py` 기본값 $4.5·40회 — 2026-10-29 승인한 라운드 상한)을 넘으면 시작하지 않는다. 돌다가 묶음 예산(`--batch-budget-usd`, 기본은
  예상 × 1.5)을 넘으면 멈춘다. 누계 비용이 $10 단위를 넘을 때마다(단가를 모르면 20회마다) 멈추고 확인을 받는다.
- **사람이 놓친 주장**: `report` 는 정답지가 있는 성적서마다 시스템만 찾은 주장(짝이 없는 추출 주장, 회차를 합쳐 같은 문장·칸·종류·인용은
  한 줄)을 판정표 `놓친주장_<태그>.csv` 로 출력 폴더에 쓴다(열: 번호·문장번호·칸·종류·인용 구절·진짜 주장인가(예/아니오)·메모). 사람이
  판정 칸을 채워 정답지 폴더에 `<태그>.missed.csv` 로 두면, 다음 `report` 가 "예" 줄을 보탤 목록 `보탤주장_<태그>.csv`(정답지 주장 표
  꼴)로 내고 `검증결과.json` 의 `missed_claims` 에도 싣는다. 그 줄을 정답지에 보태 추출 재현율·정밀도를 다시 재서 `검증결과.json` 에
  보태기 전(`extraction.pooled`, 성적서별 `runs`)과 뒤(`extraction.pooled_with_additions`, 성적서별 `with_additions`)를 둘 다 싣는다.
  정답지 파일 자체는 고치지 않는다. 문장번호가 빈 줄을 "예"로 두면 멈춘다(사람이 문장번호를 적는다).
- **명령 예(V2 — 기준 고정·결함 검사 뒤, 진짜 저장소 루트에서)**: 상한은 장부 누계를 포함한 라운드 상한이다.

  ```
  export JUDGE_LIVE_BUDGET_USD=4.5 JUDGE_LIVE_MAX_RUNS=40      # 2026-10-29 승인(기본값과 같다 — 올릴 때만 바꾼다)
  venv/bin/python scripts/judge_validate.py status --ledger ../JUDGE_ROUND/검증/장부.csv
  venv/bin/python scripts/judge_validate.py run reproducibility --mode verify --live           # 3건 × 2회 = 6회 ≈ $0.90 (멈추면 같은 명령)
  venv/bin/python scripts/judge_validate.py run reproducibility --mode verify --live --yes     # 찍힌 예상을 보고 시작
  venv/bin/python scripts/judge_validate.py run defects --mode verify --live --yes             # 결함 3개 × 1회 ≈ $0.45
  venv/bin/python scripts/judge_validate.py run sham --mode verify --live --yes                # sham 1회 ≈ $0.15
  venv/bin/python scripts/judge_validate.py report --mode verify                               # 05_결과/검증결과.json
  venv/bin/python scripts/judge_validate.py sheets --mode verify --allow-sealed                # 40문항 · 겹침 10
  ```

**그 밖의 스크립트**

| 스크립트 | 하는 일 |
|---|---|
| `scripts/judge_live.py` | 실호출 실행기. `--live` 가 없으면 진짜 클라이언트를 만들지 않고 `.env` 도 읽지 않는다. 한 실행 = 장부 한 줄. 하위 명령 `status`·`smoke`(합성 문장 실호출 확인)·`seal-generate`(검증용 판 4 요청마다 실제 작업 경로로 서술을 만들어 봉인 — 이미 봉인된 폴더면 거부)·`pilot`(개발 입력으로 채점 실측, `--narrative template\|ai`)·`job`(개발 판 4 입력 하나로 생성 + 사다리). 상한·확인 규칙은 위 "예산"과 같다(`judge_validate.py` 가 이 파일의 장부·상한·확인을 그대로 쓴다) |
| `scripts/judge_cost_report.py` | 비용·시간 집계(읽기만). `--ledger <장부.csv> [--job <내부 기록.json> …] [--mode live] [--human-minutes N] [--json]`. 장부의 단계 이름(끝 `_judge` 와 검증 실행기의 `validate_<묶음>` 은 채점, 끝 `_generate` 는 생성)으로 나누고, 작업 내부 기록으로 모듈별 시간·토큰·비용을 모은다. 비용 모르는 줄이 있으면 그 합은 비운다. 봉인 폴더 경로를 주면 멈춘다. 앱을 import 하지 않는다 |
| `scripts/judge_paths.py` | 검증 도구들의 경로 비교 한 곳(위 dev 경계·봉인 거부). 표준 라이브러리만 |
| `scripts/judge_annotate.py` | 봉인 서술의 주장 표시지(문장 표·빈 주장 표)·안내서 만들기. `--sealed <봉인 폴더> --out <정답지 폴더>`. 이미 채운 주장 표는 덮어쓰지 않는다 |
| `scripts/judge_criteria_manifest.py` | 기준 묶음 지문 쓰기·고정(14.7) |

### 14.10 가짜 LLM 개발 서버 (`scripts/dev_fake_llm_server.py`)

브라우저에서 판 4 작업을 "검증 중 → 통과/보류"까지 실호출 없이 보려고 쓴다. 운영 진입점(`uvicorn app.main:app`)과 다르다.

```bash
venv/bin/python scripts/dev_fake_llm_server.py --port 8000 --judge pass [--judge-delay 3]
```

- 앱 시작 뒤 모든 LLM 클라이언트(서술 Anthropic, 매핑·심판 OpenAI)를 가짜로 바꾸고, 첫 요청 전에 모두 가짜인지 단정한다(아니면 종료).
  키는 빈 문자열로 덮는다(지우면 `.env` 에서 다시 채워지므로). DB 는 임시 sqlite 만 받는다. 검증 기록 잠금을 끈다(`JUDGE_CRITERIA_LOCK=off`).
- `--judge pass`(위반 0·모순 0 → 통과) · `error`(심판 호출이 늘 연결 끊김 → 보류 judge_error, 다시 만들기 있음) · `refuse`(심판 거절 →
  보류 judge_error, 다시 만들기 없음). 매핑은 늘 실패해 규칙 매핑으로 강등된다.
- `--judge-delay 초`: 가짜 심판이 너무 빨리 끝나 "검증 중" 단계가 화면에 안 잡힐 때 호출마다 기다린다(작업 마감보다 짧게).
- `app/` 는 `scripts/` 를 import 하지 않는다(시험이 단정).

### 14.11 심판 설정 (환경변수 — 코드 기본값 = 운영값)

| 이름 | 기본 | 뜻 |
|---|---|---|
| `OPENAI_API_KEY` | (없음) | 매핑과 같은 키. 없으면 판 4 서술은 규칙 문장 + 보류(no_key) |
| `JUDGE_MODEL` / `JUDGE_EFFORT` | `gpt-6.1-sol` / `medium` | 심판 4모듈 모델·추론 강도(모르는 강도는 기본값) |
| `JUDGE_EXTRACT_MODEL` / `JUDGE_EXTRACT_EFFORT` | `gpt-6-luna` / `low` | 주장 추출 모델·추론 강도 |
| `JUDGE_REPORTS_PER_HOUR` | 서술 지갑과 같은 값 | 심판 지갑(보고서 수). 소진이면 보류(budget) |
| `JUDGE_SLOTS` | 2 | 동시 채점 수 |
| `JUDGE_ALERT_WEBHOOK_URL` | (없음) | 운영자 알림 웹훅(http·https 만, 비면 로그만) |
| `JUDGE_CRITERIA_LOCK` | (켜짐) | `off` 면 검증 기록 잠금을 끈다 — **시험·가짜 개발 서버 전용, 운영 금지** |

- **모델·추론 강도는 기준 묶음(`criteria/model.json`)에도 적혀 지문에 든다.** 코드 기본값과 `model.json` 이 같은지는 시험이 본다. 환경변수로
  모델·강도를 `model.json` 과 다르게 두면 검증 기록 잠금이 잠근다(model_mismatch — 판 4 는 모두 보류 judge_error, 14.8). 바꿀 때는 환경변수가
  아니라 `model.json` 과 코드 기본값을 함께 고치고 버전을 올려 다시 검증한다(14.7).
- 검증 실행기 dev 허용 목록에 폴더를 보탤 때: `JUDGE_DEV_DIRS`(경로를 `:` 로 여럿, 검증 폴더는 적어도 거부).
- 검증 도구 전용: `JUDGE_VALIDATION_DIR`(검증 폴더), `JUDGE_LIVE_BUDGET_USD`·`JUDGE_LIVE_MAX_RUNS`(실호출 상한).

### 14.12 시험

심판 시험은 `tests/test_judge_*.py` 다. 실호출은 하지 않는다(가짜 OpenAI는 `tests/judge_fakes.py`). 계약 사본 `tests/contract/judge_bundle_ed4.json`·
`judge_material_ed4.json` 은 프론트 `src/test/contract/` 와 같은 바이트여야 하고(옆 저장소가 있을 때만 대조), 고칠 때는 두 저장소와 sha256 을
함께 고친다. 판 3 정답 폴더(§13.5)는 심판 코드가 판 3 을 한 글자도 바꾸지 않았는지 지킨다.
